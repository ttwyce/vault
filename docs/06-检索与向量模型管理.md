# 06 · 检索与向量模型管理

## 1. 混合检索架构

单一检索方式都不够用：

- 纯 FTS：搜「CRDT」能命中，搜「那个讲多端同步的文章」命中不了
- 纯向量：语义能召回，但精确关键词（人名、版本号、代码标识符）经常失手

所以做三路召回 + 融合：

```
用户查询
   ├─→ [A] FTS5 BM25          → top 50
   ├─→ [B] 向量 KNN            → top 50
   └─→ [C] 结构化过滤          → 约束集合（kind / 时间 / 标签 / 归档状态 / 是否含 AI 日记）
                                    ↓
                          RRF 融合（k = 60）
                                    ↓
                          重排（可选：时间衰减 + 置顶加权）
                                    ↓
                          返回 20 条 → UI 卡片
```

### 1.1 RRF 融合

```
score(d) = Σ_i  1 / (k + rank_i(d))      k = 60

其中 i ∈ {BM25, Vector}
```

优点：不需要对不同分数量纲做归一化，鲁棒，几乎不用调参。

**时间衰减**（可选加权）：`final = rrf_score × (1 + 0.3 × exp(-days/180))`
—— 让半年前的内容不总是压过三年前的，但不至于完全沉底。

### 1.2 查询预处理

| 步骤 | 说明 |
|---|---|
| 意图识别 | 含「上个月 / 去年 / 最近」→ 提取时间范围，转成结构化过滤 |
| 引号精确 | `"flutter_gemma"` → 走 FTS 精确短语 |
| 类型限定 | 「那篇日记」→ `kind IN (3, 4)` |
| 停用词 | 中文「的、了、是」等，只在 FTS 侧处理 |
| 长度判断 | 查询 < 4 字符 → 降权向量（短查询向量效果差），提升 FTS 权重 |

### 1.3 中文分词

> ⚠️ **本节已于 2026-11-08 用实测推翻并重写。**
> 原文写「`unicode61` 对中文按字切分，召回率高但精度低」—— **这是错的**。
> 实测（`test/sqlcipher_probe_test.dart`）：`unicode61` 把**连续汉字串当成一个 token**，
> 所以 `MATCH '同步'` 对 `'增量同步'` 返回 **0 条**。不是精度低，是**完全搜不到**。

三种方案实测对比：

| 方案 | 中文 2 字词（如「同步」） | 中文 4 字词 | 英文 | 结论 |
|---|---|---|---|---|
| `unicode61` 原样索引 | ❌ 0 条 | ❌ 0 条 | ✅ | 不可用 |
| `trigram` 内建分词器 | ❌ 0 条（要求子串 ≥ 3 字符） | ✅ | ✅ | 不可单独用 |
| **`unicode61` + 应用层按字切分 + 短语查询** | ✅ 1 条 | ✅ 1 条 | ✅ | **采用** |

**采用方案的做法**（`lib/data/search/cjk_segmenter.dart`）：

```dart
// 索引侧与查询侧用同一个函数，这一步不对称就一定搜不到
String segment(String s) => s
    .replaceAllMapped(RegExp(r'[\u4e00-\u9fff\u3400-\u4dbf]'), (m) => ' ${m[0]} ')
    .replaceAll(RegExp(r'\s+'), ' ')
    .trim();

// 入库：'增量同步' → '增 量 同 步'
// 查询：'同步'    → 短语查询 MATCH '"同 步"'
```

三个要点：

1. **必须用短语查询**（加双引号）。否则 `同 步` 会变成两个独立 token 的 OR，
   「同步」和「步同」都会命中，还会跨词误召回（实测 `同步删除` 能匹配到
   「冲突合并与删除策略」的错位组合）。
2. **英文保持原样**，不切分 —— `unicode61` 对拉丁文本的处理本来就是对的。
3. **不引入**重型分词库（jieba 的 Dart 移植），也**不用** `simple` 扩展：
   预编译的 SQLCipher 里没有这个 C 扩展，自己编译会把「一行 pubspec」变成构建工程。

代价：索引体积约 2 倍（每个汉字一个 token）。5000 条笔记的 FTS 索引从约 4MB 变成 8MB，
可以接受。查询延迟无明显变化。

**仍待验证**：混合检索（FTS + 向量 + RRF）里 FTS 这一路的召回率是否够用。
如果按字切分导致噪声过多，再考虑给 FTS 结果加「短语紧邻加分」。


## 2. 向量存储

```sql
CREATE TABLE entry_vec (
  entry_id    TEXT PRIMARY KEY,
  model_id    TEXT NOT NULL,
  dim         INTEGER NOT NULL,
  vec         BLOB NOT NULL,     -- int8 量化
  computed_at INTEGER NOT NULL
);
```

- 使用 `sqlite_vector` 的 `vec0` 虚拟表或 `vector_full_scan` 做 KNN
- **存储用 int8 量化**：768 维 × 1 字节 = 768B/条；5 万条 ≈ 38MB，完全可接受
- **不要降维**：5 万条全维 float32 也才 153MB，为省空间降维是伪需求

### 2.1 分块策略

| 类型 | 分块规则 |
|---|---|
| note / thought / diary | ≤ 512 token 不分块；超出按段落切，overlap 64 token |
| bookmark（正文） | 按段落切 400 token，overlap 80，最多 20 块（超出只取前 20 块） |
| credential | **不向量化**（永不进入任何模型） |

分块结果作为独立向量条目，`entry_id` 相同、`chunk_idx` 不同（存在 `entry_vec_chunk` 表中，
或在 `entry_vec` 加 `chunk_idx` 列）。检索命中后聚合到 entry 粒度再展示。

## 3. 向量模型清单

| 模型 | 参数 | 维度 | 上下文 | 磁盘 | 语言 | 许可 | 定位 |
|---|---|---|---|---|---|---|---|
| **bge-small-zh-v1.5** | 24M | 512 | 512 | ~25 MB（int8） | 中文为主 | MIT | 内置默认，开箱可用 |
| multilingual-e5-small | 118M | 384 | 512 | ~120 MB | 100+ | MIT | 备选小模型 |
| **EmbeddingGemma 300M** | 308M | 768（MRL 512/256/128） | 2048 | ~200~330 MB | 100+ | Gemma Terms | ⭐ 主推 |
| Qwen3-Embedding-0.6B | 595M | 1024（MRL） | 32K | 396 MB(Q4) / 639 MB(Q8) | 100+ | Apache 2.0 | 中文最强，进阶 |

### 3.1 选型结论

- **内置** `bge-small-zh-v1.5`：25MB，不增加包体压力，让用户在下载任何东西前语义搜索就能用
- **主推** `EmbeddingGemma 300M`：端侧性价比最优，<200MB 内存，768 维可裁，100+ 语言
- **进阶** `Qwen3-Embedding-0.6B`：中文检索明显更好，但要接受 396MB 和两个配置坑
- **不选**：`bge-m3`（1.2GB 太重）、`nomic-embed-text-v1.5`（英文中心）、
  `all-MiniLM-L6-v2`（纯英文）、Jina v3/v5（**CC BY-NC 禁商用**）

### 3.2 两个必须配置对的坑

**坑 A：EmbeddingGemma 需要任务前缀**

```
query 侧： "task: search result | query: {用户输入}"
doc  侧： "title: {标题} | text: {正文}"
```

不加前缀不报错，但召回率明显下降。**必须写进 manifest，索引和查询各用各的模板。**

**坑 B：Qwen3-Embedding 需要 last-token pooling + 指令前缀**

```
pooling: last（不是 mean！）
query:   "Instruct: Given a note search query, retrieve relevant notes\nQuery: {q}"
doc:     不加前缀
```

如果运行时只支持 mean pooling，效果会崩且不报错。**上线前必须用自有语料做 top-1 命中率对照测试。**

## 5. 下载器设计

### 5.1 源优先级

```
1. ModelScope（魔搭）   国内直连最快
2. hf-mirror.com        HF 镜像
3. huggingface.co       官方
4. 用户自定义镜像 URL    企业内网 / 自建
5. 用户自己的 WebDAV     /vault/models/<id>.gguf（可选开关）
```

每个源独立重试；校验通过即成功；全源失败则标记失败并提示。

### 5.2 下载流程

```
点击下载
  → 检查磁盘可用空间（需 ≥ disk_bytes × 1.5）
  → 创建 models/<id>/download.part
  → background_downloader 下载（支持 Range 断点续传）
  → 进度回调（bytes / total / speed / ETA）
  → 完成后 sha256 校验
      ├ 通过 → rename 为正式文件 → state = 2（就绪）
      └ 失败 → 删除 .part → 切换下一个源 → 3 次后 state = 3（损坏）
```

### 5.3 存储与备份排除（必须做）

| 平台 | 位置 | 排除备份 |
|---|---|---|
| Android | `getApplicationSupportDirectory()/models/` | `dataExtractionRules` / `fullBackupContent` 排除 `models/` |
| iOS | 同上 | 对目录设置 `NSURLIsExcludedFromBackupKey = true` |
| Windows | `%LOCALAPPDATA%` | 不落 OneDrive 同步目录 |

**不排除备份的后果**：用户 iCloud/Google 空间被几百 MB 模型吃掉，且可能触发商店审核质疑。

### 5.4 复用 WebDAV 作为模型镜像

```
/vault/models/<model_id>.gguf
```

设备 A 下载后上传 → 设备 B/C 直接从用户自己的网盘拉取。
解决：国内网络波动、重复消耗流量、离线设备安装。

做成可选开关（默认关），上传前提示体积，并计入配额统计。

## 6. 索引重建

### 6.1 触发场景

| 场景 | 范围 |
|---|---|
| 首次下载模型 | 全量 |
| 切换活跃模型 | 全量（旧向量全部作废） |
| 新条目写入 | 单条 |
| 条目编辑 | 单条（重新分块） |
| 从云端拉取新条目 | 单条 |
| 模型文件损坏重下 | 全量 |

### 6.2 任务设计

```
job_queue: type='reembed_all', payload={model_id, cursor}

执行：
  1. 若切换模型 → DELETE FROM entry_vec WHERE model_id != new_model
  2. 按 updated_at 升序分批（每批 20 条）
  3. 每批：分块 → 推理 → 写 entry_vec → 更新 cursor
  4. 每批完成后写回 cursor（可中断）
  5. 进度 = 已处理 / 总数，写入 job_queue.payload
```

**性能目标**：中端手机 15~40 条/秒，5000 条 < 8 分钟。
Windows 桌面可 100+ 条/秒。

### 6.3 降级策略（重要）

| 状态 | 检索行为 | UI |
|---|---|---|
| 无模型 | 纯 FTS + 结构化过滤 | 设置页提示「下载模型可启用语义搜索」 |
| 模型下载中 | 纯 FTS | 静默 |
| 索引构建中 | FTS + **已构建部分**的向量 | 顶部细进度条，可点开查看 |
| 索引完成 | 完整混合检索 | 无提示 |

**任何情况下检索都可用**，只是质量不同。这是「降级可用」原则的体现。

## 7. 向量同步

```
/vault/vec/<hmac32(entry_id)>.enc
  解密后：{ "model_id": "...", "dim": 768, "dtype": "int8", "bytes": "<base64>" }
```

| 规则 | 说明 |
|---|---|
| 加密上传 | 向量是语义指纹，明文上传等于泄露内容大意，必须加密 |
| 拉取后解密 | 写入本地 `entry_vec`（明文，受 SQLCipher 保护） |
| **model_id 不匹配** | 直接丢弃，标记该条需重算；**绝不混用不同模型的向量** |
| dim 不匹配 | 同上 |
| 传输体积 | int8 768 维 ≈ 800B/条，5 万条 ≈ 40MB，可接受 |
| 是否可关 | 提供开关「向量同步」（关闭则换设备需全量重算） |

## 8. 检索 UI 设计

### 8.1 结果卡片

```
┌──────────────────────────────────────────┐
│ 📄 多端同步的冲突处理方案                  │
│ 「…CRDT 在移动端维护成本太高，建议先用   │
│   行级三方合并 + 冲突副本…」              │
│ 2026-08-12 · 笔记 · 命中：语义            │
└──────────────────────────────────────────┘
```

- 摘要高亮命中词
- 显示命中来源（关键词 / 语义 / 两者）
- 显示归档状态徽章（原站存活 / 已失效 / 有快照）

### 8.2 空结果处理

```
无结果
  → 提示「换个说法试试」+ 3 个查询改写建议（由端侧模型生成）
  → 若 FTS 有结果但向量无 → 提示「已启用关键词匹配，下载语义模型可获得更好效果」
```

## 9. 验收标准

| # | 标准 |
|---|---|
| B1 | 5000 条数据下，混合检索 P95 < 300ms |
| B2 | 中文查询「上个月那篇讲同步冲突的文章」能命中正确条目（top 3） |
| B3 | 精确标识符（`flutter_gemma`）能通过 FTS 精确命中 |
| B4 | 无模型 / 下载中 / 构建中三种状态检索均可用 |
| B5 | 切换模型后旧向量全部清除，无混用 |
| B6 | 模型文件不进系统备份（三端验证） |
| B7 | 下载中断后能断点续传，校验失败能换源 |
| B8 | 换设备后向量同步成功，无需重算 |

## 1. `WriteGateway` 存在的唯一理由

**让"实体变更"和"变更日志"不可能分开。**

同步引擎靠 oplog 重放保证零丢失。如果某个调用点直接
`db.into(entries).insert(...)` 而忘了写 oplog，那条变更就永远不会被推送 ——
用户会看到「这条笔记在 A 设备上有、B 设备上没有」，而且**没有任何报错**。

这类 bug 不会在开发时暴露，只会在用户换设备时暴露，且无法事后修复
（数据已经在本地了，但没有推送记录，不知道要推什么）。

所以全项目只有这一个写入口，把两件事关进同一个事务：

```
一次写入 =
  ① 读旧状态（算 rev / base）
  ② 旧状态归档进 entry_history（三方合并的 base）
  ③ 新状态封进 ItemEnvelope（加密）
  ④ 写 oplog（outbox）
  ⑤ 改 entry
  ⑥ 更新 FTS 索引
  ⑦ 回收站增删
  ⑧ 持久化 HLC
  —— 同一事务，要么全成，要么全败
```

### 1.1 原子性是被测出来的，不是被声明的

`test/write_gateway_test.dart` 里有一条故意制造的失败：

```dart
final broken = WriteGateway(
  ...,
  segmenter: (String _) => throw StateError('索引写入故意失败'),
);
await expectLater(broken.writeEntry(...), throwsA(isA<StateError>()));
expect(await count('entry'), 0);         // 实体必须回滚
expect(await count('oplog'), 0);         // oplog 必须回滚
expect(await count('entry_history'), 0); // 历史也必须回滚
```

选"索引写入"作为失败点，是因为它发生在 oplog 与 entry 都已写完之后 ——
如果事务边界写错，数据库里就会留下一条「有实体但没有 oplog」的幽灵记录，
或者「有 oplog 但没有实体」的悬空推送。这两个都是同步引擎的毒药。

## 2. 条目加密信封：一个差点做错的格式

这是本轮**唯一一个"做错了以后要重新加密全库"的决定**，值得单独讲。

### 2.1 问题的形状

原计划：`AAD = entity + id + rev`，密文里什么都不带。接收端会卡住：

> 解密需要 AAD → AAD 需要 rev → rev 在密文里 → 解不开。

三条出路，只有第三条成立：

| 方案 | 问题 |
|---|---|
| AAD 只绑 id，rev 放进密文 | 旧版本密文可以被重放到新版本位置（回滚攻击） |
| rev 编码进文件名 | rev 变了文件就得改名，而文件名是 `HMAC(id)`，一改名就是一次删除+新建，破坏 `If-Match` |
| **明文头携带 entity/id/rev，AAD = 头部字节本身** | ✅ |

### 2.2 最终格式

```
┌──────┬────────────┬──────────────────┬──────────────────────┐
│ 1 B  │   2 B      │      N B         │       剩余            │
│ 信封 │ 头部长度    │  头部（JSON）     │  SecretWrapper 封装   │
│ 版本 │ 大端 uint16 │  {e, i, r}       │ 版本+nonce+密文+tag   │
└──────┴────────────┴──────────────────┴──────────────────────┘
```

头部用 `Canonical.json` 序列化（键排序、无空白），保证同样的
`(entity, id, rev)` 永远产出同样的头部字节 —— 否则 AAD 会随机变化，
同一条数据的两次加密会得到两个互不兼容的密文。

### 2.3 这个设计额外买到三样东西

1. **AAD 就是头部原始字节**，不需要「先解析再用解析结果拼 AAD」——
   少一次可能不一致的推导。篡改头部任何一个字节都会导致认证失败。
2. **本地 oplog 与云端 item 文件字节完全一致**，推送时可以直接 PUT，
   不需要「用 A 解密再用 B 加密」那一轮多余的 CPU，
   也不需要在那段时间里让明文出现在内存里。
3. **同步层可以只读头部做冲突预判**：`ItemEnvelope.parse` 不验签、不解密，
   就能知道"这条远端文件对应哪个 id、哪个 rev"。

第 2 条也是 `VaultKeys` 里**没有 oplog 子密钥**的原因：oplog 里存的就是
条目快照，与云端 item 文件是同一份明文。域分离靠 AAD，不靠换密钥。

### 2.4 防篡改的端到端验证

测试里两条：

```dart
// 把 A 的 payload 塞进 B 的行 —— 信封头与行上的 entityId 对不上
await expectLater(gateway.readSnapshot(rowB), throwsA(isA<StateError>()));

// 改头部一个字节 —— AAD 变了，认证失败
final tampered = ItemEnvelope.parse(bytes)..// 把 '1' 改成 '2'
await expectLater(tampered.open(key: key), throwsA(isA<SecretUnwrapException>()));
```

## 3. rev 与 content_hash 的语义

### 3.1 content_hash 只覆盖"内容"

```
content_hash = sha256(canonical({kind, title, body, meta}))
```

**不含** `updated_at` / `hlc` / `rev` / `deleted`。

理由：把它们算进哈希会让「内容没变、只是被同步了一次」也被判定为内容变化，
从而在设备之间制造无穷的假冲突。

`meta` 必须**先解码再参与哈希**：直接哈希 JSON 字符串的话，
`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 会算出两个不同哈希，而它们语义完全一样。
测试里有一条专门验这个。

### 3.2 内容没变就不产生新版本

```dart
if (snapshot.contentHash == previous.contentHash) {
  return EntryWriteResult(snapshot: previous, oplogSeq: -1, changed: false);
}
```

这条很关键：编辑器保存按钮、自动保存、切换焦点都可能触发一次
"内容相同的写入"。每次都 `rev + 1` 的话，同步会在设备之间来回推送
一堆内容一样的版本，冲突副本也会被这些空变更刷屏。

### 3.3 空操作不写 oplog

重复删除、恢复一条没删的条目 —— 都是幂等空操作，`changed = false`，
**不写 oplog**。否则一次误触就会把一条无意义的变更推送到所有设备，
制造出根本不存在的新版本。

### 3.4 状态机（本地）

| 当前状态 | create | update | delete | restore |
|---|---|---|---|---|
| 不存在 | ✅ rev=1 | ❌ `not_found` | ❌ `not_found` | ❌ `not_found` |
| 正常 | ❌ `exists` | ✅ rev+1 | ✅ rev+1 + 进回收站 | ⚪ 空操作 |
| 已删除 | ❌ `exists` | ❌ `already_deleted` | ⚪ 空操作 | ✅ rev+1 + 出回收站 |

`update` 拒绝已删除的条目而**不自动复活**：复活是 `restore` 的语义，
混在一起会让"删除"在同步合并时无法判断用户意图（见 04 文档的冲突矩阵，
"修改 vs 删除"那一行要求明确区分"编辑"和"取消删除"）。

### 3.5 回收站保留 30 天

删除时把**同一份信封**写进 `trash` 表，`expireAt = deletedAt + 30 天`。
测试断言了这个差值必须是 `Duration(days: 30)` —— 这类"约定值"
最容易在重构时被悄悄改掉。

## 4. 历史版本：三方合并的 base

每次更新 / 删除 / 恢复，都把**旧状态**归档进 `entry_history`（加密快照），
并裁剪到最近 5 条。

```
DELETE FROM entry_history WHERE entry_id = ? AND rev NOT IN (
  SELECT rev FROM entry_history WHERE entry_id = ? ORDER BY rev DESC LIMIT 5
);
```

测试里连做 9 次更新，断言留下的恰好是 `rev = 4..8`
（当前版本 `rev=9` 在 `entry` 表里，不在历史表）。

### 4.1 为什么必须存 base

三方合并需要三份数据：`base`（上次同步成功的版本）、`local`、`remote`。
**没有 base 就只能生成冲突副本**，而冲突副本对用户来说是"又多了两条要处理的东西"。

这是同步引擎里唯一无法事后补救的部分：如果更新时没存 base，
那次更新就永远无法被自动合并，只能靠用户手工挑。

## 5. HLC 持久化

每次写入都在同一事务里 upsert `device_watermark.max_hlc`。

为什么不批量/延迟持久化：**崩溃后重启可能生成比历史更小的时钟值**，
合并时会被误判成旧版本，导致旧数据覆盖新数据。这是"零丢失"承诺的
直接威胁，不值得为省一次 upsert 去赌。

`HlcClock` 的 `_last` 在内存里，`restore()` 在启动时从
`device_watermark` 读回。这一步在 M2 的应用启动流程里接上。

## 6. ActivityLogger：埋点必须在业务之前

### 6.1 为什么不能后补

AI 日总结的数据源只有这张表。用户问「我上个月干了什么」，答案不能靠现算 ——
只能靠当时记下来的。**埋点晚一天，那天就永远缺一段。**

### 6.2 核心设计：合并窗口，而不是流水账

直接每次事件插一行会立刻爆炸：用户翻列表会连点 30 条笔记，
编辑器自动保存 10 分钟能写上百次。这样的表既没用（信息密度极低）
又贵（日总结要读几万行）。

| 事件 | 窗口 | 合并后的语义 |
|---|---|---|
| 浏览 / 归档阅读 | 30 分钟 | 一次"阅读会话"，`dwellMs` 累加 |
| 编辑 | 5 分钟 | 一次"编辑会话"，不区分击键 |
| 搜索 | 60 秒 | 同一关键词的连续输入（防打字机式刷屏） |
| 创建 / 剪藏 | 不合并 | 每次都算独立事件 |

合并后的粒度恰好是日总结想要的：**「读了 5 篇、写了 3 条、搜了 8 次」**，
而不是「点击了 47 次」。

### 6.3 `dwellMs` 是这张表最有价值的字段

它区分「扫了一眼」和「读了五分钟」。没有它，日总结只能说
"你看了 12 篇文章"，有它才能说"你在 WebDAV 那篇上花了 18 分钟"。

用法：进入页面 `view(id)`，离开时 `view(id, dwell: 实际停留)`。
第二次调用落进同一窗口，dwell 累加，`ts` 更新为会话结束时刻。

### 6.4 隐私边界

`query` 字段（搜索词）是**敏感数据** —— 它暴露用户在关心什么。

- 只存本地库，受 SQLCipher 保护
- **不参与同步**（`activity` 不在 `SyncEntity` 列表里）
- 不随日志导出、不进崩溃上报
- 日总结只用它做聚类，不外发

测试里有一条专门断言：记了三种活动之后，`oplog` 表必须仍然为空。

### 6.5 日摘要：喂给模型的不是原始时间线

```dart
final summary = await logger.summarizeDay(day);
// → totalEvents, countByKind, dwellByKind,
//   touchedEntryIds, searchQueries, firstAt, lastAt
```

原始时间线可能有几百行，直接塞 prompt 会浪费 token 且噪声极大。
摘要里 `touchedEntryIds` 是去重的条目 id —— 日总结据此去取标题与摘要
（只读摘要不读全文，这是 07 文档 §成本控制的要求）。

`headline` 刻意用「新建 1 条 · 阅读 1 次」这种朴素措辞，不用
"洞察""总结" —— 这一行是**事实**，AI 生成的判断在别处，两者不能混。

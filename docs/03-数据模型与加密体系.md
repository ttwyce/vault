# 03 · 数据模型与加密体系

## 1. 加密分层（先建立心智模型）

```
┌─────────────────────────────────────────────────┐
│ 第 1 层：静态加密 —— SQLCipher 整库加密            │
│   保护：设备丢失后被拖库                           │
│   效果：DB 文件离开设备即不可读                    │
└─────────────────────────────────────────────────┘
                     ↓ 读取后为明文（进程内）
┌─────────────────────────────────────────────────┐
│ 第 2 层：字段级 AEAD —— 上传前加密                │
│   保护：WebDAV 服务商、传输链路                    │
│   效果：云端只有密文，服务商零知识                 │
└─────────────────────────────────────────────────┘
```

**关键设计**：本地 DB 内是**明文**（受 SQLCipher 页级保护），这样 FTS5 和 sqlite-vec 才能正常工作。
字段级加密只发生在**同步边界**（PUT 之前加密、GET 之后解密）。

这是一个刻意的取舍：如果字段级加密落库，全文索引和向量索引都无法建立，
整个「找回」功能就废了。安全边界由 SQLCipher + 设备锁屏共同保证。

### 1.1 第 1 层已定案：SQLCipher（2026-11-08 实测通过）

```yaml
# pubspec.yaml —— 全部实现就这一处
hooks:
  user_defines:
    sqlite3:
      source: sqlcipher
```

`sqlite3` 3.9 的 native-assets 钩子直接提供 SQLCipher 预编译产物，
Android（arm/arm64/ia32/x64）、iOS（arm64 + sim）、Windows（x64/ia32/arm64）全覆盖。
实测 `PRAGMA cipher_version` 返回 `4.20.0 community`，错误密钥打开会 HMAC 校验失败，
FTS5 与 WAL 均正常。详见 [02 §11.2](02-技术选型与依赖.md) 与 `test/sqlcipher_probe_test.dart`。

**被否决的方案**：应用层字段加密 + 明文索引。原因是 `entry_fts` 里存的是正文 token 流，
`entry_history` / `trash` / `activity` 也都含明文 —— 拿到 db 文件就能还原全部内容。
字段级 AEAD 仍然要做，但它是**第 2 层（同步边界）**的必需品，不能替代第 1 层。

#### 打开数据库的三条硬规则

实现见 `lib/data/db/database_opener.dart`（`VaultDatabaseOpener`，全项目唯一 open 入口）。

```dart
// 1. 先 PRAGMA key，再碰任何数据
//    注意外层双引号不能省：SQLite 的 PRAGMA 解析器不接受裸 blob 字面量
raw.execute('PRAGMA key = "x\'$hexKey\'";');

// 2. 断言一：链接的必须是 SQLCipher（普通 SQLite 返回空集）
if (raw.select('PRAGMA cipher_version;').isEmpty) {
  throw StateError('链接的不是 SQLCipher');
}

// 3. 断言二：密钥必须真的生效（没有密钥上下文时 cipher_salt 返回空集）
if (raw.select('PRAGMA cipher_salt;').isEmpty) {
  throw StateError('PRAGMA key 没有生效，数据库会以明文创建');
}
```

**为什么需要两条断言**（这是实测踩出来的，不是理论推演）：

本项目全局用 SQLCipher，所以「忘了执行 `PRAGMA key`」的连接**照样会报出版本号**。
只查 `cipher_version` 的话，一条明文数据库会安安静静地建出来、测试全绿、
上线后密码明文躺在磁盘上。`PRAGMA cipher_salt` 是唯一能区分
"设了 key"与"忘了设 key"的探针。

另外配一条文件级校验：库落盘后，文件头不能是明文 SQLite 的
`SQLite format 3\0`（加密库的头是随机字节）。作为第三道保险。

#### 改主密码不需要 rekey

`DEK_local` 是被 KEK 包裹后存在安全存储里的，不是从主密码直接算出来的。
所以「改主密码」= 用新 KEK 重新包裹同一个 `DEK_local`，**毫秒级完成**，
不需要对一个几百 MB 的库跑 `PRAGMA rekey`。

同理，生物识别解锁 = 系统安全区解出被包裹的 `DEK_local`，跳过 Argon2id，冷启动更快。


## 2. 密钥层级

> **实现见 [16 密钥与恢复码](16-密钥与恢复码.md)**（含 Argon2id 实测耗时）。
> 本节只保留心智模型。

```
用户主密码 (用户记忆)
    │
    ├─ Argon2id(salt, m=64MB, t=3, p=4, 32B)
    ↓
   KEK (Key Encryption Key)
    │
    ├─ 包裹 → DEK (每个 vault 一个，随机 32B，明文只在内存)
    │              │
    │              ├─ HKDF → K_item      = HKDF(DEK, info="vault/item/v1")
    │              ├─ HKDF → K_blob      = HKDF(DEK, info="vault/blob/v1")
    │              ├─ HKDF → K_name      = HKDF(DEK, info="vault/name/v1")
    │              ├─ HKDF → K_meta      = HKDF(DEK, info="vault/meta/v1")
    │              ├─ HKDF → K_oplog     = HKDF(DEK, info="vault/oplog/v1")
    │              └─ HKDF → K_local_db  = HKDF(DEK, info="vault/local-db/v1")
    │
    └─ 包裹 → 同一把 DEK（用恢复码派生的 KEK'）
```

> **与原设计的一处偏离**：原本计划"另外包裹一把 `DEK_local` 给本地库用"。
> 实现时改为**从 DEK 派生** `K_local_db`。理由是恢复码只需要恢复**一个**秘密 ——
> 两个被包裹的 DEK 意味着恢复码也要包两份，任何一份丢失都会让
> "换设备后本地库打不开"变成无法自愈的状态。域分离的目的仍然达到。
> 详见 [16 §2.1](16-密钥与恢复码.md)。

| 密钥 | 存放位置 | 生命周期 |
|---|---|---|
| 主密码 | 不存储 | 用户记忆 |
| KEK | 仅内存 | 解锁期间 |
| DEK（明文） | 仅内存 | 解锁期间 |
| DEK（密文，KEK 包裹） | `meta.enc.wrapped_dek` | 永久 |
| DEK（密文，KEK' 包裹） | `meta.enc.recovery_wrapped_dek` | 永久 |
| 恢复码 24 词 | 用户抄写；系统不保存明文 | 永久（直到重置） |

**Argon2id 参数**：`m=64MiB, t=3, p=4`，与 Bitwarden 默认值一致。
桌面 JIT 实测 **2.1 秒**（不是设计阶段推测的 0.6~1.2s），移动端待测。
参数写入 `meta.enc`，未来可升级（用旧参数解、新参数重新包裹）。
完整数据见 [16 §3](16-密钥与恢复码.md)。

## 3. 加密算法与格式

| 对象 | 算法 | 说明 |
|---|---|---|
| 字段（title/body/meta） | XChaCha20-Poly1305 | 24B nonce 随机，附加数据 = `entry_id + rev + field_name`（防重放与字段替换） |
| blob（快照/附件） | XChaCha20-Poly1305（分块） | 每块 1MB，独立 nonce，块序号进 AAD |
| 文件名 | HMAC-SHA256(K_name, entry_id) 取前 32 hex | 防元数据泄露 |
| 内容校验 | SHA-256（明文 canonical form） | 合并后校验，防合并 bug |
| 备份导出 | 同上 + 明文 zip 打包 | 导出前二次确认密码 |

**AAD 设计很重要**：把 `entry_id + rev + field_name` 作为附加认证数据，
可以防止攻击者把 A 条目的密文挪到 B 条目、或把旧版本密文重放到新版本位置。

## 4. 表结构

> **完整建表脚本已迁至 [13 数据模型总表](13-数据模型总表.md)**（20 张表的统一 DDL）。
> 本文只保留加密相关的字段语义，避免两处维护产生偏差。

### 4.1 哪些字段需要加密

| 表 | 需加密字段 | 说明 |
|---|---|---|
| `entry` | title / body / meta | 上传前字段级 AEAD；本地明文（受 SQLCipher 页级保护） |
| `credential` | username / password / totp_secret / notes / custom_fields | 整行敏感；`custom_fields` 内 `secret:true` 的项与密码同级 |
| `category` / `tag` | name / color | 分类名可能含项目名，一并加密 |
| `conversation` / `message` | title / content / tool_calls / citations | 会话内容可能包含笔记原文 |
| `entry_history` | payload | 已是加密快照 |
| `trash` | payload | 已是加密快照 |

### 4.2 不加密的字段

`id` / `hlc` / `rev` / `created_at` / `updated_at` / `content_hash` / `deleted` / `sort_order` / 各类计数
—— 这些是同步与合并的元数据，加密后无法参与比对。

### 4.3 AAD 约定

字段级加密的附加认证数据统一为：

```
AAD = entry_id || rev || field_name
```

防止攻击者把 A 条目的密文挪到 B 条目，或把旧版本密文重放到新版本位置。

## 5. HLC（混合逻辑时钟）

格式：`{ms:016x}:{counter:04x}:{deviceId}`，例如 `0000018F2A3B4C5D:0003:devA`。

**为什么不用普通时间戳**：三端时钟会漂移，用 `updated_at` 做 LWW 会出现「慢的时钟永远输」的问题。
HLC 保证：

- 单调递增（同一设备）
- 跨设备可比（接收远端 HLC 时，本地时钟至少推进到 `max(local, remote)+1`）
- 字符串字典序 = 逻辑序（可直接用于 SQL 排序与比较）

**实现要点**：
```dart
// 伪代码
String nextHlc() {
  final now = clock.now().millisecondsSinceEpoch;
  if (now > _lastMs) { _lastMs = now; _counter = 0; }
  else { _counter++; }
  return '${_lastMs.toRadixString(16).padLeft(16,'0')}:'
         '${_counter.toRadixString(16).padLeft(4,'0')}:$_deviceId';
}
```

**持久化**：`_lastMs` / `_counter` 必须落盘（存 `device_watermark` 或独立 kv 表），
否则 App 重启后可能生成重复 HLC。

## 6. canonical form 与 content_hash

`content_hash` 用于合并后校验，必须**确定性**：

```
canonical = jsonEncode({
  "title": title ?? "",
  "body": body ?? "",
  "meta": canonicalizeJson(meta)   // 键排序、去除空白
})
content_hash = sha256(utf8(canonical))
```

`canonicalizeJson` 规则：键按字典序递归排序、数字统一为整数或固定精度、不输出空格。
**三端必须用完全相同的实现**，否则跨端校验必然失败。建议写一份 Dart 实现 + 一份测试向量，
在 CI 里对固定样本断言 hash 值。

## 7. 恢复码机制

**这是产品最大的口碑风险点：主密码丢失 = 数据永久丢失。**
完整实现与容错规则见 [16 密钥与恢复码](16-密钥与恢复码.md) §5。要点：

1. 首次创建 vault 时**强制**生成 24 词 BIP-39 恢复码并引导用户抄写
2. 恢复码派生 `KEK'`，用 `KEK'` 再包裹同一把 DEK 存入 `meta.enc`
3. 用户确认「我已抄写」的方式：随机抽取 3 个词让用户填入（防止直接点下一步）
4. 设置页可随时重新生成恢复码（旧恢复码立即失效，需主密码验证）
5. 文案必须明确：「我们无法帮你找回密码。没有恢复码，数据将永久无法解密。」

**为什么是 BIP-39 而不是自造词表**：24 词的最后 8 bit 是校验和，
抄错一个词在设置当下就能发现。没有校验和，手抄错误完全无法检测，
等于把「永久丢失」的概率从接近 0 抬到不可接受。

## 8. `meta.enc` 结构

```json
{
  "schema": 3,
  "vault_id": "uuid",
  "created_at": 1731052800000,
  "kdf": { "algo": "argon2id", "m": 65536, "t": 3, "p": 4, "salt": "base64" },
  "wrapped_dek": "base64",           // KEK 包裹
  "recovery_wrapped_dek": "base64",  // KEK' 包裹
  "active_embedding_model": "embeddinggemma-300m-q8",
  "embedding_dim": 768,
  "item_count": 3412,
  "device_ids": ["devA", "devB"]
}
```

**注意**：`meta.enc` 是**全局写热点**，只在 vault 级配置变化时写（换 embedding 模型、设备增删）。
**绝不用它做变更检测**（见 04 文档 §2）。

## 9. 数据库迁移策略

| 场景 | 处理 |
|---|---|
| 本地 schema 升级 | drift `MigrationStrategy`，每次迁移写单元测试 + 回滚测试 |
| 云端 `meta.schema` 高于本地 | **拒绝同步**，提示「请升级 App」，防止低版本破坏高版本数据 |
| 云端 `meta.schema` 低于本地 | 允许同步，同步后写回新 schema（但要求所有设备已升级） |
| `vault_id` 不匹配 | **拒绝同步**，提示用户确认是否切换 vault |

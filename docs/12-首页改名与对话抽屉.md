# 12 · 首页改名「聊天」与对话抽屉

## 1. 为什么原来叫「今天」

这个命名不是随手取的，它承担了三个设计意图。

**① 把产品从「档案柜」变成「助理」**

知识库类产品打开第一屏通常是分类目录：笔记本列表、文件夹树、标签云。用户要先用 3~5 秒做一次「我该去哪」的决策，才开始干活。

「今天」把这个决策删掉了 —— 你打开时面对的不是分类，是**此刻**：昨天存了什么、AI 帮你处理了什么、有什么等你决定。

**② 时间是唯一不需要用户维护的维度**

分类要建、标签要打、文件夹要整理，这些都会随着使用量增长而变成负担。而"今天"是自动的：不管用户多懒，今天的日期永远存在。

**③ 给 AI 一个"主动"的位置**

这个产品的 AI 不是被召唤的，是常驻的。它需要一个自然的开口 —— "早上好。昨天你存了 3 条跟 WebDAV 限流有关的东西，要我合成一篇吗？"

这句话放在「今天」下面是汇报，放在「笔记列表」下面就成了打扰。**命名决定了 AI 能不能主动说话。**

参考来源：`today.ai` 用的就是这套逻辑（"记得你的生活，在你开口前行动"）。

---

## 2. 为什么现在改成「聊天」

引入对话抽屉之后，「今天」这个名字和新结构产生了三处冲突：

| 冲突 | 说明 |
|---|---|
| **语义重复** | 抽屉里第一个分组标题就是「今天」，如果页面本身也叫「今天」，会读成"今天 → 今天 → 某条对话" |
| **结构错位** | 这个页面现在的本质是「会话列表 + 当前会话」，是聊天产品的标准骨架，不叫聊天反而让人困惑 |
| **认知成本** | 新用户看到「今天」，不知道能干什么；看到「聊天」，立刻知道"可以说话、可以丢东西进来" |

**但"今天"没有被丢掉** —— 它降级成了抽屉里的第一个分组标题。时间感还在，只是从"页面名"变成了"组织方式"。

## 3. 交互改动

### 3.1 新增元素

| 位置 | 元素 | 行为 |
|---|---|---|
| 左上 | 三横杠（菜单） | 点击 → 抽屉从左侧滑出，遮罩淡入 |
| 右上 | 「＋ 开启新对话」 | 点击 → 清空主区，进入空白会话（草稿态） |
| 标题下 | 当前对话条 | 显示当前会话标题 + 时间 + 引用数 |

### 3.2 抽屉内容

### 3.3 交互规则

| 场景 | 规则 |
|---|---|
| 打开抽屉 | 从左侧滑出 280ms（移动端覆盖 72% 宽度，桌面 340px）；遮罩 `rgba(ink, 26%)` |
| 搜索 | 输入即筛，匹配**标题 + 消息正文**，命中处高亮；`↑↓` 选择，`↵` 打开，`Esc` 清空 |
| 新建对话 | 抽屉顶部按钮 → 关闭抽屉 + 主区清空 + 光标聚焦输入框 |
| 选中对话 | **抽屉自动收起**（200ms）→ 主区加载该会话 → 顶部当前对话条更新 → 列表项高亮 |
| 当前对话标识 | 抽屉内：便签黄底 + 左 3px 红条 + 轻微倾斜；主区：标题下方常驻一条「当前对话 · 标题 · 时间」 |
| 空会话 | 新建后未发消息就切走 → 不落库，直接丢弃（避免产生大量空会话） |
| 关闭抽屉 | 点遮罩 / 按 `Esc` / 点右上关闭 |

### 4.3 数据层

会话不塞进 `entry`，用两个独立实体。**完整建表脚本见 [13 数据模型总表](13-数据模型总表.md) §2.4**，此处仅列要点：

```sql
CREATE TABLE conversation (
  id          TEXT PRIMARY KEY,
  title       TEXT,                -- 自动取首条消息前 20 字，可改名
  group_id    TEXT,                -- 可空；为空则按日期自动分组
  created_at  INTEGER,
  updated_at  INTEGER,
  hlc         TEXT NOT NULL,
  message_count INTEGER DEFAULT 0,
  deleted     INTEGER DEFAULT 0
);

CREATE TABLE message (
  id              TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL,
  role            INTEGER NOT NULL,  -- 1 user / 2 assistant / 3 tool
  content         TEXT,
  tool_calls      TEXT,              -- JSON
  citations       TEXT,              -- JSON，指向 entry id
  created_at      INTEGER,
  hlc             TEXT NOT NULL
);
CREATE INDEX idx_msg_conv ON message(conversation_id, created_at);
```

搜索走 FTS5：`conversation_fts(title, body)`，与现有 `entry_fts` 同一套分词策略。

## 5. 关键实现思路

**① 抽屉用 overlay，不改变主区布局**

抽屉是 `Stack` 上的覆盖层，不是 `Row` 的一个子项。这样开关抽屉时主内容**不重排**，避免列表滚动位置跳动。

```dart
Stack(children: [
  ChatBody(),                       // 主区，宽度恒定
  if (drawerOpen) Backdrop(),       // 遮罩，点击关闭
  AnimatedPositioned(               // 抽屉滑入
    duration: AppMotion.panel,      // 280ms
    left: drawerOpen ? 0 : -drawerWidth,
    child: ConversationDrawer(),
  ),
])
```

**② 新对话是"草稿态"，不立即落库**

```dart
// 点击「开启新对话」
state = state.copyWith(draft: Conversation.empty(), currentId: null);

// 直到用户发出第一条消息，才真正插入 conversation 记录
onFirstMessageSent: () {
  if (state.draft != null) {
    final conv = repo.create(state.draft!);   // 此时才写 oplog
    state = state.copyWith(currentId: conv.id, draft: null);
  }
}
```

否则用户每点一次「新对话」就多一条空记录，抽屉很快会被垃圾填满。

**③ 选中会话 = 关抽屉 + 换内容 + 复位滚动**

```dart
Future<void> select(String id) async {
  closeDrawer();                    // 先收起，避免遮挡加载过程
  await controller.load(id);
  scrollController.jumpTo(maxExtent); // 定位到最新消息
}
```

**④ 分组优先用"日期"，用户分组作为可选覆盖**

默认：今天 / 昨天 / 本周 / 更早（按 `updated_at` 相对当前时间算）。
如果用户建了分组（如"WebDAV 项目"），则该会话归到用户分组下，不再出现在日期分组里。

**⑤ 当前对话在抽屉里的高亮**

便签黄底 + 左 3px 红条 + 轻微倾斜（`rotate(-0.4deg)`）。倾斜是关键 —— 手绘风格里"当前项"必须比其他项多一个视觉属性，否则只是一块色块。

## 6. 对现有功能的影响

| 功能 | 影响 | 说明 |
|---|---|---|
| AI 对话内容 | **无** | 只改了外层容器，消息流渲染逻辑不变 |
| 引用卡片 / 工具卡 | 无 | 仍在消息流内，`citations` 字段不变 |
| 底部导航 | 仅标签 | 图标不变（气泡图标本来就适合"聊天"），`今天` → `聊天` |
| 桌面侧栏 | 仅标签 | 同上 |
| 抽屉外的其它页面 | 无 | 抽屉是聊天页局部状态，不涉及全局路由 |
| 同步 | 新增两个实体 | `conversation` / `message` 走独立同步通道，复用 oplog + If-Match；不影响 `entry` |
| 检索 | 新增一路索引 | `conversation_fts` 与 `entry_fts` 并列，搜索结果分区展示 |
| 日总结 / AI 日记 | 无 | 仍然读 `activity` 与 `entry`，不读会话内容 |

**唯一需要注意的**：会话与笔记是两套东西。会话是"过程"，笔记是"结果"。AI 在对话里整理出来的东西，仍然要显式落成 `entry` 才算数 —— 这个边界不能因为有了"聊天"就模糊掉。

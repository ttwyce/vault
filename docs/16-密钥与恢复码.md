## 1. 一句话概括

**用户记一个密码，系统守住一把 32 字节随机密钥，其余全部从它派生。**

主密码不直接加密任何数据。它只做一件事：算出 KEK，用 KEK 把 DEK 包起来。
DEK 才是真正加密数据的那把钥匙。这个「包裹」结构换来三件事：

| 需求 | 因为包裹结构而变成 |
|---|---|
| 改主密码 | 重新包裹 DEK，**毫秒级**，不用 rekey 几百 MB 的库 |
| 恢复码 | 另一个 KEK' 包裹同一把 DEK，两把钥匙开同一把锁 |
| 生物识别解锁 | 系统安全区取出包裹好的 DEK，**跳过 Argon2id** |

## 2. 密钥层级（已实现版）

```
主密码（用户记忆）
   │
   ├─ Argon2id(盐, m=64MiB, t=3, p=4) ──→ KEK ──包裹──→ DEK 密文 ──存 meta.enc
   │
恢复码 24 词
   │
   ├─ BIP-39 解码 → 256 bit 熵
   ├─ HKDF-SHA256(info="vault/recovery-kek/v1") ──→ KEK' ──包裹──→ 同一把 DEK 的密文
   │
DEK（32 B 随机，明文只在内存）
   │
   └─ HKDF-SHA256 派生五条子密钥：
        ├─ "vault/item/v1"      条目快照（oplog payload / 历史 / 回收站 / 云端 item）
        ├─ "vault/blob/v1"      快照 / 附件
        ├─ "vault/name/v1"      云端文件名 HMAC
        ├─ "vault/meta/v1"      meta 内敏感字段
        └─ "vault/local-db/v1"  本地 SQLCipher 密钥
```

> **没有单独的 oplog 子密钥**（早期设计里有，实现时删掉了）。
> oplog 里存的就是条目快照，与云端 item 文件是同一份明文 ——
> 用同一把 `item` 子密钥意味着推送时可以直接 PUT oplog 里的字节，
> 不需要「用 A 解密再用 B 加密」那一轮多余 CPU 和明文窗口。
> 域分离靠 AAD，不靠换密钥。详见 [17 写入路径](17-写入路径与活动埋点.md) §2.3。

### 2.1 与 03 文档的一处偏离：`DEK_local` 改为派生

03 文档 §2 原写的是「另外包裹一把 `DEK_local` 给本地库用」。实现时改成**从 DEK 派生**，理由：

- **恢复码只需要恢复一个秘密。** 两个被包裹的 DEK 意味着恢复码也要包两份，任何一份丢失都会让「换设备后本地库打不开」变成一个无法自愈的状态。
- 派生是零成本的，而多存一份被包裹的密钥就多一份不一致的可能。
- 域分离的目的仍然达到：`local-db` 子密钥与 `item` 子密钥在密码学上无关，调试时 dump 到本地库密钥不会连带泄露云端密文的解密能力。

代价：换 DEK 必须连带 rekey 本地库。但 DEK 只在「全量重新加密」这种极端场景才换，正常路径（改主密码）只重新包裹 DEK，不碰这里。

## 3. Argon2id：实测数据，不是推测

**这一节是本文档最重要的部分。**

设计阶段写的是「低端 Android 约 0.6~1.2s」，那是推测。`cryptography` 包里的
Argon2id 是**纯 Dart 实现**（会起 isolate 并行，但每个 lane 的计算仍是 Dart 代码），
Dart 的 Argon2 吞吐通常只有 C 实现的 1/3 ~ 1/5。所以必须实测。

`test/kdf_perf_probe_test.dart` 的输出（桌面 JIT，`flutter_tester`）：

| 参数 | 耗时 | 评价 |
|---|---|---|
| m=19MB, t=2, p=1（OWASP 最低线） | **606 ms** | 太弱，不用于密码库 |
| m=32MB, t=3, p=4 | **1,224 ms** | 折中选项 |
| **m=64MB, t=3, p=4（当前采用）** | **2,147 ms** | 与 Bitwarden 默认值一致 |

### 3.1 结论：保留 64 MB，但必须改 UX

选 64 MB 不是因为「更安全总是更好」，而是因为**这是密码管理器这个品类的行业基线**：
Bitwarden 的 Argon2id 默认参数就是 `m=64MB, t=3, p=4`。参数低于这个值，
在安全审计和用户信任上都要额外解释。

但 2.1 秒（移动端大概率 1.5~4 秒）意味着三条硬性 UX 要求：

| 要求 | 原因 |
|---|---|
| 解锁页必须显示进度，不能只有一个静止的输入框 | 2 秒无反馈会被当成卡死，用户会强行杀进程 |
| 派生必须在后台 isolate，不能阻塞首帧 | 否则输入密码后整个界面冻住，连转圈都转不动 |
| 提供生物识别 / 「记住 15 分钟」 | 让「每次冷启动都等 2 秒」变成「一天一次」 |

> **待补的真机数据**：以上是桌面 JIT 数字。AOT 编译通常快 2~3 倍，
> 但手机 CPU 又比桌面慢。净效果需要真机实测（当前无真机连接，按约定不构建）。
> 真机数据出来后回填此表。

### 3.2 为什么 `parallelism` 不能按设备自适应

Argon2 的 `p` 是**算法参数**，参与最终哈希的计算。同一份数据在 p=4 和 p=1 下
派生出完全不同的 KEK。所以它必须三端一致、随 vault 持久化，不能"4 核用 4、
2 核用 2"。这也是为什么它必须写进 `meta.enc`。

### 3.3 参数升级路径

参数存在 `meta.enc.kdf` 里，所以升级是安全的：

```
用旧参数解出 DEK → 用新参数重新包裹 → 写回 meta
```

已发出的 vault 永远保留它创建时的参数，不会因为 App 升级而打不开。

## 4. 包裹格式

```
┌──────┬────────────┬──────────────────┬──────────┐
│ 1 B  │   24 B     │      N B         │   16 B   │
│ 版本 │   nonce    │    密文（DEK）    │   tag    │
└──────┴────────────┴──────────────────┴──────────┘
```

算法 XChaCha20-Poly1305。32 字节 DEK 包裹后是 **73 字节**。

### 4.1 为什么是 XChaCha 而不是 ChaCha

普通 ChaCha20-Poly1305 只有 96 bit nonce，随机生成时 birthday bound 在
2^48 次加密后出现碰撞风险。XChaCha 的 192 bit nonce 允许**每次都用纯随机 nonce**，
不需要计数器、不需要跨设备协调状态。

### 4.2 AAD 绑定用途 —— 这条不能省

AAD 固定为 `vault/v1/<用途>/<vaultId>`，用途只有两个值：`dek` 和 `recovery-dek`。

**没有 AAD 会怎样**：攻击者能编辑 `meta.enc`（它是明文 JSON），把
`wrapped_dek` 和 `recovery_wrapped_dek` 互换位置。两段密文长度相同、
都是「某把 KEK 包裹的 32 字节」，都能通过 AEAD 认证 —— 唯一能区分它们的
就是 AAD。绑定之后，任何搬运都会导致认证失败。

测试用例 `把两段包裹密文互换位置解不开` 固定住了这条。

### 4.3 版本字节放在最前面

不塞进 AAD 而是单独一个字节：将来换算法时，老版本 App 能立刻识别出
「这不是我能解的格式」并给出明确提示，而不是拿错算法去解、
最后报一个含糊的「认证失败」。

## 5. 恢复码

### 5.1 规格

| 项 | 值 |
|---|---|
| 词表 | BIP-39 英文 2048 词（随包，`bip39_english.dart`） |
| 词数 | 24（256 bit 熵 + 8 bit 校验和） |
| 派生 | HKDF-SHA256 → KEK'，**不跑 Argon2** |
| 存放 | `meta.enc.recovery_wrapped_dek` |

### 5.2 为什么用 BIP-39 而不是自造词表

恢复码是这个产品**唯一的数据救命绳**。主密码丢了、设备全丢，用户只能靠
手抄的 24 个词把库解回来。这要求词表满足三件事：

1. **拼写无歧义** —— 2048 词里任意两个词的前 4 个字母都不同。用户抄到一半
   忘了全词，输入 `aban` 就能唯一确定 `abandon`。
2. **带校验和** —— 24 词的最后 8 bit 是前 256 bit 的 SHA-256 校验和。
   **抄错一个词，在设置恢复码的当下就能发现**，而不是三年后换设备时才发现解不开。
3. **可审计** —— 有大量第三方实现，用户可以拿任何工具验证自己的词，
   不需要信任我们的实现。

自造词表在三条上都会失败，尤其是第 2 条。没有校验和，手抄错误完全无法检测，
等于把「永久丢失」的概率从接近 0 抬到不可接受。

### 5.3 为什么恢复码不跑 Argon2id

很多实现会对恢复码也跑一遍慢哈希，那是错的。恢复码是 **256 bit 真随机熵**，
没有可爆破空间，Argon2 带来的安全增益是零，代价却是
「灾难恢复时用户要在一台陌生设备上多等 2 秒，还可能因为内存不足失败」。

所以恢复码走 HKDF（微秒级），主密码走 Argon2id（秒级）。两条路径分开。

### 5.4 输入容错

用户是在**手抄纸上认字**，不是在键盘上打字。所以解析器容忍：

| 情况 | 处理 |
|---|---|
| 大小写 | 不敏感 |
| 分隔符 | 空格 / 换行 / 制表 / 中英文逗号 / 顿号 / 分号 / 竖线，都当分隔符 |
| 序号前缀 | `1. abandon`、`1、abandon`、`1) abandon`、`(1) abandon` 都能读 |
| 缩写 | **4 字母以上**唯一前缀自动补全（`aban` → `abandon`） |

不容忍的（明确报错而不是猜）：

- 少于 4 个字母的片段 —— 3 字母在词表里普遍有歧义（`sol` → solar/soldier/solid/solution/solve）
- 前 3 字母有歧义时，必须完整输入

错误信息必须指出**是第几个词**，因为用户会拿纸逐个核对。

### 5.5 首次设置的强制确认

`RecoveryCode.pickPositions(3, rng)` 抽 3 个不重复位置（升序），
`code.matches(position, answer)` 校验用户回忆。

这一步不做，后面会有大量用户丢数据 —— 而且他们会在最需要数据的时候才发现。

## 6. `meta.enc` 结构

```json
{
  "schema": 1,
  "vault_id": "0192f0aa-1111-7222-8333-444455556666",
  "created_at": 1731052800000,
  "kdf": {
    "algo": "argon2id",
    "version": 19,
    "memory_kb": 65536,
    "iterations": 3,
    "parallelism": 4,
    "hash_length": 32,
    "salt": "base64…"
  },
  "wrapped_dek": "base64…",
  "recovery_wrapped_dek": "base64…",
  "active_embedding_model": null,
  "embedding_dim": null,
  "item_count": 0,
  "device_ids": []
}
```

### 6.1 这个文件是明文的，这是刻意的

它必须能在**解锁之前**被读到 —— 没有它就不知道 KDF 盐和参数，也就无法
从主密码算出 KEK。所以不能整体加密。

真正敏感的只有两段被包裹的 DEK，它们是 AEAD 密文，没有 KEK 解不开。
其余字段泄露的信息量很低，但足够用来做变更检测与防误连。

### 6.2 三个「看起来能省但不能省」的字段

| 字段 | 省掉的后果 |
|---|---|
| `vault_id` | 用户把两个 vault 指向同一个 WebDAV 目录时，会静默合并成灾难 |
| `kdf` 参数 + 盐 | 未来调参后，老 vault 永远解不开 |
| `schema` | 新版本写入的库被老版本 App 打开，静默丢字段 |

### 6.3 序列化必须确定

`toJsonString()` 按 key 排序输出。否则同一份 meta 每次写出的字节不同，
WebDAV 上会制造无意义的 `If-Match` 冲突。测试里有一条
`同一份 meta 两次序列化字节完全一致` 固定住它。

### 6.4 解析即校验

`Argon2Params.fromJson` 直接拒绝越界参数。这不是洁癖，是**防拒绝服务**：
`meta.enc` 是用户可以手工编辑的明文 JSON，如果有人写入
`memory_kb: 2147483647`，设备一解锁就 OOM 崩溃，而且每次重装都复现。

## 7. 四条解锁路径

| 场景 | 入口 | 走 Argon2 | 耗时 |
|---|---|---|---|
| 日常冷启动 | `unlock(passphrase)` | ✅ | ~2s（移动端待测） |
| 灾难恢复 | `unlockWithRecoveryCode(input)` | ❌ | 微秒级 |
| 生物识别 | 系统安全区取包裹的 DEK | ❌ | 系统决定 |
| 首次创建 | `create(passphrase)` | ✅ ×3 | ~6s（含自检） |

### 7.1 创建时的自检不能省

`create()` 在返回之前会**分别用主密码和恢复码各解一次**，确认解出的 DEK
与创建时一致。多花 20ms，换掉一个具体的灾难：

如果包裹逻辑有 bug（AAD 拼错、recovery 分支用错 purpose），用户会拿到一个
**看起来创建成功、实际永远打不开**的 vault —— 而且是在三个月后换设备时才发现。

自检失败直接抛 `StateError`，绝不把这样的 vault 交给用户。

### 7.2 无法区分「密码错」和「文件坏」

这是 AEAD 的性质，不是实现缺陷。所以 UI 文案必须写
**「主密码不正确，或该文件已损坏」**，不能写「密码错误」——
否则用户会一直重试一个其实正确的密码。

`SecretUnwrapException` 的存在就是为了把这条事实明确传给上层。

## 8. 这套设计不保护什么

诚实清单。这些不是「以后补」，是**架构层面的边界**：

| 不保护 | 原因 |
|---|---|
| 解锁后的进程内存 | Dart 没有 `mlock`，GC 会搬动对象。`destroy()` 只能清掉我们能控制的那一份 |
| 主密码弱 | Argon2id 抬高成本，但 `123456` 仍然是 `123456`。需要在创建时做强弱检测 |
| 已解锁设备被物理控制 | 内存里有明文 DEK。靠系统锁屏 + 自动锁定超时缓解 |
| 侧信道（时序、功耗） | 纯 Dart 实现不保证常量时间。真实威胁模型里攻击者拿不到这个级别的物理接触 |
| 恢复码被拍照泄露 | 恢复码等价于库的备份钥匙。UI 必须警告「不要截图、不要存云相册」 |
| 云服务商看到 `meta.enc` | 它能看到 vault 创建时间、条目数、设备数。第 2 层字段加密保护的是**内容**，不是**元数据** |

## 9. 代码地图

```
lib/core/crypto/
  secret_bytes.dart     密钥字节原语（复制语义 / 常量时间比较 / 单向指纹 / 擦除）
  argon2_params.dart    Argon2id 参数 + 校验 + JSON；KdfSalt
  kdf.dart              两条派生入口（主密码走 Argon2，恢复码走 HKDF）
  secret_wrapper.dart   XChaCha20-Poly1305 包裹 + AAD 用途绑定
  vault_keys.dart       DEK → 六条子密钥（带缓存）
  bip39_english.dart    2048 词表（生成文件，勿改）
  recovery_code.dart    BIP-39 编解码 + 输入容错 + 抽查
  vault_meta.dart       meta.enc 结构与确定性序列化
  vault_lock.dart       创建 / 解锁 / 改密码 / 重置恢复码
```

### 9.1 一个实现细节：指纹用哈希而不是密钥字节

`SecretBytes.fingerprint` 早期版本取的是首尾各 4 字节，等于把 64 bit
真实密钥写进日志。虽然剩余 2^192 空间仍不可爆破，但「日志里出现密钥材料」
本身就不该开这个先例 —— 日志会被贴进 issue、上传到崩溃平台、留在别人的终端里。

改成 `sha256(key)` 的前 4 字节：不含任何密钥信息，同时保持可比性。
测试里有一条断言指纹不能是 `toHex()` 的子串。

其中最有价值的五条：

1. **BIP-39 官方向量** —— 用独立 Python 实现复算过，不是凭记忆写的断言
2. **密文互换必须失败** —— 这是 AAD 存在的唯一理由
3. **改密码后 DEK 不变** —— 「只重新包裹」这个设计的核心承诺
4. **旧恢复码立即失效** —— 重置恢复码的安全边界
5. **创建自检** —— 防止产出「看起来成功但永远打不开」的 vault

## 1. 这一层解决什么问题

前面几轮做的都是"零件"：加密、数据库、写入、埋点。它们各自有测试，
但**没有任何东西把它们串起来**。这一层就是那根线：

```
main()
 ├─ FontService.boot()          字体先就绪（首帧不能闪）
 ├─ VaultStorage.readMeta()     读 meta.enc，决定首帧显示哪一页
 └─ ProviderScope
      └─ VaultApp
           └─ VaultGate          ← 全 App 唯一的路由判断
                ├─ OnboardingPage   首次创建 + 恢复码
                ├─ UnlockPage       输密码 / 输恢复码
                ├─ AppShell         主界面
                └─ _FatalErrorPage  meta.enc 损坏
```

## 2. 五个状态，一次 `switch`

```dart
enum VaultStatus {
  needsSetup,   // 本机没有 vault → 走创建流程
  locked,       // 有 vault 但未解锁
  unlocking,    // 正在派生 / 打开数据库（**持续 2 秒以上**）
  unlocked,     // 数据库与写入口可用
  failed,       // 致命错误：重试没有意义
}
```

### 2.1 为什么把 `failed` 单独分出来

普通错误（密码错）可以重试。`failed` 意味着**重试也没用** ——
典型是 `meta.enc` 损坏：没有它就无法派生出 KEK，换任何密码都打不开。

所以致命错误页**不提供"重试"按钮**。那是在骗用户 —— 他会在一个
永远不会成功的操作上反复尝试，然后以为是自己密码记错了。

那一页只做三件事：说清发生了什么、给出可执行的下一步（从备份恢复 `meta.enc`）、
让用户能把错误信息复制走求助。

### 2.2 `unlocking` 期间仍渲染解锁页

```dart
case VaultStatus.locked:
case VaultStatus.unlocking:
  return const UnlockPage();
```

不切到一个独立的"加载页"：那会让页面在派生的 2 秒里被整个替换掉，
视觉上闪一下。解锁页自己根据 `isBusy` 切换成转圈状态，DOM 结构不变。

## 3. 闸门的判断顺序（不能改）

```dart
// ① 恢复码优先于一切
if (state.recoveryCode != null) return const OnboardingPage();

switch (state.status) { ... }
```

第一条是**整个 App 里最容易写错的一行**。

创建 vault 成功后，状态已经是 `unlocked` 了 —— 但用户还没抄下那 24 个词。
如果这时候按状态直接进主界面，那 24 个词就**永远看不到了**
（系统只存被包裹的 DEK，不存词本身）。

所以闸门的第一判断不是 `status`，而是"内存里还有没有未确认的恢复码"。

## 4. `VaultStorage`：文件布局与两条硬规则

```
<appSupport>/
  meta.enc         vault 元数据（明文 JSON，含两段被包裹的 DEK）
  device_id        本机标识（UUIDv7，纯文本）
  vault.db         SQLCipher 加密库
  fonts/           字体子系统（见 docs/15）
```

### 4.1 规则一：写 `meta.enc` 必须先写临时文件再 rename

```dart
await temp.writeAsString(meta.toJsonString(), flush: true);
await temp.rename(target.path);
```

直接覆写的话，写到一半断电会留下一个半截 JSON ——
而它是解锁的**唯一入口**，等于永久锁死整个库。

### 4.2 规则二：读不懂 ≠ 不存在

```dart
Future<VaultMeta?> readMeta();   // 不存在 → null
                                 // 存在但解析失败 → 抛 VaultMetaException
```

把"文件损坏"当成"首次使用"是灾难性的：App 会引导用户新建一个 vault，
用户会以为自己原来的数据没了，而实际上它就在磁盘上、只是读不懂。

所以 `VaultMetaException` 会一路冒到 `main()`，变成 `bootError`，
最后渲染致命错误页。

### 4.3 `device_id` 为什么单独一个文件

- 放 `meta.enc` → 每次写设备列表都会成为同步写热点（见 docs/04 §2）
- 放数据库 → 要先解锁才能读到，而 **HLC 在解锁过程中就需要 node**

文件内容不合法时（被手工改坏），**不静默重新生成**，而是先重命名为
`device_id.broken-<时间戳>` 再建新的。悄悄换掉会让该设备的历史 HLC
与新 id 对不上，合并时把新数据判成旧的。

## 5. `VaultSession`：只做三件事

**创建、解锁、锁定。** 所有密码学细节在 `VaultLock`，所有文件布局在
`VaultStorage`，这一层只负责"把两者接起来 + 管状态"。

### 5.1 解锁成功后的装配顺序

```
① VaultKeys.localDatabase()   → 派生本地库密钥（与内容密钥分离）
② VaultDatabaseOpener.open()  → 打开 SQLCipher 库（三道加密断言）
③ HlcClock.restore()          → 从 device_watermark 读回时钟
④ WriteGateway / ActivityLogger → 注入同一个 db + keys + clock
```

第 ③ 步不做的话：App 重启后 HLC 从零开始，可能生成比历史更小的值，
同步合并时被判成旧版本，**旧数据覆盖新数据**。

### 5.2 锁定的顺序不能反

```dart
if (opener != null) await opener.close();   // 先关库
unlocked?.dispose();                        // 再清密钥
```

反过来的话，drift 在关闭时可能还有挂起的写事务，而密钥已被清零，
会抛一个很难查的错。

### 5.3 重复创建必须被拦住（两道闸）

`createVault` 会生成**一把全新的 DEK** 并写进 `meta.enc`。而 `meta.enc` 是
解锁的唯一入口 —— 覆盖之后旧 DEK 的包裹结果消失，**老数据永久打不开，
而且全程没有任何报错**。

所以有两道闸：

| 闸 | 位置 | 拦什么 |
|---|---|---|
| 状态守卫 | `createVault` 开头 `if (state.hasVault)` | 闸门判断错、将来重构误调 |
| 文件守卫 | `VaultStorage.writeMetaIfAbsent` | 状态判断被绕过（纵深防御） |

正常路径上闸门不会把用户送到创建页（有 vault 时显示解锁页），
但这类"少一行判断就永久丢数据"的地方，宁可多一道。

### 5.4 创建失败要区分"meta 是否已落盘"

```dart
if (metaWritten) {
  // 本机现在确实有 vault 了 → locked，让用户用刚设的密码重试
} else {
  // 还没写盘 → needsSetup，允许重新创建
}
```

一律回到 `needsSetup` 是错的：`meta.enc` 已经写好的情况下，那个状态会
引导用户**再创建一次**，等于把刚写好的 meta 覆盖掉。

### 5.5 失败时立刻清掉已算出的密钥

```dart
} on VaultUnlockException catch (error) {
  unlocked?.dispose();   // 不留在内存里
  state = state.copyWith(status: VaultStatus.locked, error: error.message);
}
```

## 6. 解锁页的两个设计约束

### 6.1 不伪造进度百分比

Argon2id **没有进度回调**。做一个从 0 涨到 90% 再卡住的进度条是欺骗 ——
用户会以为卡死了。

所以只显示两样真实的东西：

- 一个不确定的转圈（`CircularProgressIndicator`）
- **已用秒数**（`state.elapsed`，每秒刷新）

配一句「正在派生密钥，通常需要 2 秒左右」。用户看到秒数在走就知道没死。

### 6.2 错误文案原样显示，不改写

`VaultUnlockException` 的文案是精心写过的：

> 主密码不正确，或该文件已损坏。两者无法区分 —— 认证失败时不泄露原因。

如果 UI 自己改写成「密码错误」，用户会一直重试一个**其实正确**的密码。
这是 AEAD 的性质，不是实现缺陷，必须如实告知。

## 7. 首次创建：两个阶段在同一个页面里

```
阶段一：设主密码        → createVault()
阶段二：展示 24 词恢复码 → acknowledgeRecoveryCode()
```

靠 `state.recoveryCode == null` 判断当前在哪一阶段。

### 7.1 阶段一必须显著展示的那句话

> **没有恢复码，忘记主密码 = 数据永久无法解密。我们帮不了你。**

这不是免责声明，是这个产品最需要诚实的地方。

### 7.2 阶段二的核心是"让人真的抄对"

24 个词排成 4 组、每组 6 个，**每个词带全局序号**（1..24，不是每组从 1 开始）。
序号必须连续 —— 抄的人会中途停下来，靠序号才知道自己抄到第几个。

然后用 `RecoveryCode.pickPositions(3, Random.secure())` 抽 3 个位置让用户回填。
`matches()` 支持 4 字母缩写，所以用户写 `aban` 也算对。

**允许无限次重试，不锁定。** 这一步的目的是帮用户发现自己抄错了，
不是考核记忆。

## 8. 测试覆盖

`test/vault_session_test.dart`（14 条）覆盖正常路径：首次启动 / 已有 vault /
meta 损坏 / 创建 / 创建后真能写入 / 重新启动解锁 / 密码错误 / 恢复码解锁 /
恢复码抄错 / 锁定清密钥 / 锁定后可再解锁。

`test/vault_session_guard_test.dart`（7 条）覆盖**不该发生的调用**：
重复创建被拒且 `meta.enc` 一字节不变 / `writeMetaIfAbsent` 拒绝覆盖 /
缺 meta 时 `unlock` 与恢复码解锁都要给出提示（不能静默）/
`copyWith(clearHandles:)` 的置空语义。

> **写这类测试时的一个坑**：`ProviderContainer.dispose()` 只销毁 provider，
> **不会关闭会话持有的数据库句柄**。所以 tearDown 里必须先 `lock()` 再删
> 临时目录，否则 Windows 上会报 `PathAccessException: 另一个程序正在使用此文件`
> —— 而它发生在 tearDown 里，会被记成"测试失败"，掩盖掉断言其实通过了。

其中两条最值得说：

- **创建后能真的写入** —— 用 `state.gateway!` 调一次 `writeEntry`，
  验证的是"密钥 → 数据库 → 写入口"整条链路真的通了，而不只是状态字段被赋值
- **重新启动后解锁出的 DEK 指纹与创建时一致** —— 证明 `meta.enc` 的
  序列化 / 反序列化没有丢掉任何影响解密的信息

# 04 · 同步引擎设计（核心）

> 这是整个项目最关键的子系统。**如果只能认真做一件事，就做这个。**
> 验收标准只有一条：**任意并发编辑组合下，用户数据零丢失。**

## 1. 约束与设计目标

| 约束 | 后果 | 应对 |
|---|---|---|
| WebDAV 无推送 | 只能轮询 | 三级探测，让「无变化」只花 1 个请求 |
| WebDAV 无事务 | 多文件更新可能半途中断 | oplog 重放，幂等操作 |
| WebDAV 无锁（多数实现） | 并发写会互相覆盖 | `If-Match` 条件写（CAS） |
| 各服务器行为差异大 | 一套代码不一定通用 | 能力探测 + 降级路径 |
| 服务商限流 | 请求被 429/503 | 串行队列 + 请求预算 + 指数退避 |
| iOS 后台额度极少 | 无法实时同步 | 前台触发为主，文案写「打开即同步」 |

**设计目标**：

1. 常规同步（无变化）≤ 3 个请求
2. 任意中断可恢复，不产生重复或丢失
3. 冲突必留副本，删除永不吞掉未同步的编辑
4. 所有远程操作幂等

## 2. 云端目录布局

```
/vault/
├── meta.enc                          # vault 元数据（低频写，非变更检测依据）
├── devices/
│   ├── devA.json                     # 设备水位（明文，不含敏感内容）
│   └── devB.json
├── items/
│   ├── 0/ 1/ 2/ … f/                 # 16 个分片目录
│   │   └── <hmac32(entry_id)>.enc    # 一条 entry 一个文件
├── tombstones/
│   └── <hmac32(entry_id)>.enc        # 删除墓碑，TTL 90 天
├── vec/
│   └── <hmac32(entry_id)>.enc        # {model_id, dim, dtype, bytes}
└── blobs/
    ├── <sha256[0:2]>/<sha256>.bin    # 内容寻址、不可变、按需下载
    └── _tmp/<uploadId>/<part>.bin    # 大文件分片上传中转
```

**设计说明**：

| 决策 | 理由 |
|---|---|
| 一条 item 一文件 | 冲突隔离在单条，增量小，不会因一条改动上传全库 |
| 16 分片 | PROPFIND 单目录文件数控制在 N/16，避免上万文件时目录列举过慢 |
| 文件名 = HMAC(entry_id) | 不泄露标题；同时避免中文/特殊字符的 URL 编码差异问题 |
| blob 内容寻址 | 相同内容自动去重；不可变 → 永不冲突、永不需合并 |
| `devices/` 明文 | 只含 HLC 与时间戳，不含任何内容信息 |

**路径编码规范**：所有路径使用 `Uri.encodeComponent`，但**不编码 `/`**；
文件名限定为 `[0-9a-f]{32}.enc`，从根上绕开各家服务器对中文与特殊字符的处理差异。

## 3. 三级变更探测

### 3.1 L1：设备水位探测（1 个请求）

每台设备在完成同步后写入自己的水位文件：

```json
// /vault/devices/devA.json
{
  "device_id": "devA",
  "platform": "windows",
  "max_hlc": "0000018F2A3B4C5D:0003:devA",
  "last_seen": 1731052800000,
  "app_version": "1.0.3",
  "schema": 3
}
```

探测逻辑：

```
PROPFIND /vault/devices/  Depth:1
  → 得到 [{name: devA.json, etag}, {name: devB.json, etag}]

for each remote device D != self:
   if D.max_hlc > local.device_watermark[D].max_hlc  → 有变化，进入 L2
   if D.etag 变化但 max_hlc 未变                     → 无内容变化，仅更新时间戳

若全部无变化 → 同步结束（1 请求）
```

**为什么这是最优解**：设备数恒定 3~5，`devices/` 目录永远很小。
相比「PROPFIND 整个 items 目录」，请求数与响应体积都低两个数量级。

**边界情况**：`devices/` 里出现未知设备（用户新装了设备）→ 进入 L2 全量比对。

### 3.2 L2：发现变更

先做**能力探测**（缓存结果，24 小时有效）：

```
OPTIONS /vault/
  → 检查响应头 DAV 是否包含 "sync-collection"
```

| 服务器能力 | 策略 | 请求数 |
|---|---|---|
| 支持 RFC 6578（Nextcloud、部分 Synology） | `REPORT sync-collection` 一次拿全量增量 + 删除列表 | 1 |
| 不支持（坚果云、Apache mod_dav） | 16 个分片各做 `PROPFIND Depth:1` | 16 |

**PROPFIND 请求体**（只要必要属性，减小响应体积）：

```xml
<d:propfind xmlns:d="DAV:">
  <d:prop>
    <d:getetag/>
    <d:getcontentlength/>
  </d:prop>
</d:propfind>
```

**diff 逻辑**：

```
remote_set = { path → etag }
local_set  = SELECT path, etag FROM sync_state

added    = remote_set - local_set
modified = { p | remote.etag != local.etag }
deleted  = local_set - remote_set        # 服务器不支持 sync-collection 时才有意义
```

### 3.3 L3：按需拉取

只 GET `added + modified` 的文件。`blobs/` 不参与比对（内容寻址，本地没有才拉）。

**批量策略**：并发 3~4 个 GET（不是全部并发，防限流），单个失败重试 2 次后跳过并记录，下次继续。

## 4. 同步状态机

### 4.1 状态定义

| 状态 | 含义 |
|---|---|
| `IDLE` | 空闲 |
| `ACQUIRE_LOCK` | 获取单飞锁（全局 mutex） |
| `PROBE` | L1 水位探测 |
| `DISCOVER` | L2 变更发现 |
| `PULL_TOMBSTONES` | 拉取墓碑（**必须在条目之前**） |
| `PULL_META` | 拉取 meta.enc 并校验 vault_id / schema |
| `PULL_ENTRIES` | 拉取变更条目 |
| `MERGE` | 三方合并 / LWW / 冲突处理 |
| `PUSH` | 推送 oplog 待发操作 |
| `VERIFY` | 校验（content_hash 对账） |
| `PUBLISH` | 写回本设备水位 + sync_state |
| `BACKOFF` | 退避等待 |
| `FAILED` | 终止，记录错误码 |

### 4.2 状态转移表

| 当前 | 事件 | 下一状态 |
|---|---|---|
| IDLE | 触发（前台/编辑/手动/定时） | ACQUIRE_LOCK |
| ACQUIRE_LOCK | 锁已被占用 | IDLE（本次跳过，不排队堆积） |
| ACQUIRE_LOCK | 获得锁 | PROBE |
| PROBE | 无变化 且 oplog 无待发 | PUBLISH |
| PROBE | 无变化 但 oplog 有待发 | PUSH |
| PROBE | 有变化 | DISCOVER |
| DISCOVER | 成功 | PULL_TOMBSTONES |
| DISCOVER | 请求超预算 | PUSH（先推本地，剩余下次续） |
| PULL_TOMBSTONES | 成功 | PULL_META |
| PULL_META | vault_id 不匹配 | FAILED(E_VAULT_MISMATCH) |
| PULL_META | schema 高于本地 | FAILED(E_SCHEMA_TOO_NEW) |
| PULL_META | 成功 | PULL_ENTRIES |
| PULL_ENTRIES | 成功 | MERGE |
| MERGE | 全部合并成功 | PUSH |
| MERGE | 存在冲突副本 | PUSH（冲突已落库，标记待用户处理） |
| PUSH | 全部成功 | VERIFY |
| PUSH | 遇 412 | PULL_ENTRIES（重新拉取该条并再合并） |
| PUSH | 412 超过 3 轮 | 生成冲突副本 → VERIFY |
| PUSH | 网络错误 | BACKOFF |
| PUSH | 429/503 | BACKOFF（长退避） |
| VERIFY | 通过 | PUBLISH |
| VERIFY | hash 不匹配 | 回滚本次 → FAILED(E_MERGE_BUG) |
| PUBLISH | 成功 | IDLE |
| BACKOFF | 到达重试时间 | PROBE |
| BACKOFF | 超过最大重试 | FAILED(E_NET) |

### 4.3 主流程伪代码

```
sync(trigger):
  if !lock.tryAcquire(): return Skipped
  try:
    budget = RequestBudget(limit = 200)

    # --- L1 ---
    changes = await probeDevices(budget)
    if !changes && pendingOps().isEmpty: return publishAndExit()

    # --- L2 ---
    diff = await discover(budget)      # sync-collection 或 分片 PROPFIND

    # --- PULL ---
    tombstones = await pullTombstones(diff, budget)
    meta       = await pullMeta(budget)        # 校验 vault_id / schema
    remotes    = await pullEntries(diff, budget)

    # --- MERGE ---
    conflicts = []
    for each (path, remoteBytes) in remotes:
        remote = decrypt(remoteBytes)
        local  = findLocal(remote.id)
        result = merge(local, remote, base = history(local.baseRev))
        applyResult(result)
        if result.isConflict: conflicts.add(result)

    # --- 墓碑应用 ---
    for each tombstone in tombstones:
        applyTombstone(tombstone)     # 注意：编辑优先规则

    # --- PUSH ---
    for op in pendingOps(budget):
        await pushWithIfMatch(op)     # 412 则回到 merge
        op.applied = 1

    # --- VERIFY ---
    verifyHashes(affectedIds)

    # --- PUBLISH ---
    writeDeviceWatermark(nowHlc())
    updateSyncState(diff)
    logSync(result)
  finally:
    lock.release()
```

## 5. 合并与冲突

### 5.1 冲突规则矩阵（必须逐条实现并有测试）

| # | 本地 | 远端 | 动作 | 说明 |
|---|---|---|---|---|
| 1 | 无 | 有 | 直接插入本地 | 新条目 |
| 2 | 有 | 无 | 保持本地，等待推送 | 本地新建未推 |
| 3 | 修改 | 未变 | 直接 PUT（If-Match=base） | 常规推送 |
| 4 | 未变 | 修改 | 直接覆盖本地 | 本地无改动，安全 |
| 5 | 修改 | 修改 | **三方合并** → 失败则冲突副本 | 见 5.2 |
| 6 | 删除 | 未变 | 写墓碑 → DELETE 文件 | |
| 7 | 未变 | 删除 | 本地软删除进回收站 | 保留 30 天 |
| 8 | **修改** | **删除** | **编辑胜：复活条目，写新版本** | 关键规则 |
| 9 | **删除** | **修改** | **编辑胜：取消本地删除，接受远端** | 关键规则 |
| 10 | 删除 | 删除 | 幂等，仅清理 | |
| 11 | 新建 | — | UUIDv7，物理上不可能撞 | |
| 12 | 解密失败 | — | 隔离到 `quarantine/`，**不覆盖本地**，报错 | 防篡改/损坏 |

**第 8、9 条是「零丢失」的核心。** 实现时的判据：

```
若 local.deleted == 1 且 remote.rev > local.rev 且 remote 内容与 base 不同
   → 视为「删除期间对方修改了」→ 复活
若 remote 有墓碑 且 local.rev > base.rev（本地有未推的编辑）
   → 忽略墓碑，保留本地并推送新版本
```

### 5.2 三方合并算法

**前置**：必须有三份数据

- `base` = `entry_history` 中 `rev == base_rev` 的版本（base_rev 来自 `sync_state.hlc` 对应的 rev）
- `local` = 当前本地
- `remote` = 拉取的远端

**若无 base**（首次同步就撞车）→ **不做合并，直接生成冲突副本**。

```
merge3(base, local, remote):
  if local.content_hash == base.content_hash: return remote      # 只有远端变了
  if remote.content_hash == base.content_hash: return local      # 只有本地变了
  if local.content_hash == remote.content_hash: return local     # 巧合相同

  # 文本合并：按行
  localHunks  = diff(base.body, local.body)
  remoteHunks = diff(base.body, remote.body)

  if hunksOverlap(localHunks, remoteHunks):
     # 重叠 → 冲突块，两边都保留
     merged.body = applyWithConflictMarkers(base, local, remote)
     result.isConflict = true
  else:
     merged.body = applyBoth(localHunks, remoteHunks)

  # meta（JSON）→ 字段级 LWW
  merged.meta = fieldLevelLWW(base.meta, local.meta, remote.meta)
  # 特例：tags 取并集，而不是 LWW

  merged.rev  = max(local.rev, remote.rev) + 1
  merged.hlc  = nextHlc()
  merged.content_hash = sha256(canonical(merged))
  return result
```

**冲突标记格式**（沿用 git 习惯，用户容易理解）：

```
<<<<<<< 本地（设备 A，11-08 13:20）
本地版本的内容
=======
云端版本的内容（设备 B，11-08 13:25）
>>>>>>> 
```

**冲突副本命名**：`{title} (冲突副本 设备B 2026-11-08 13:25)`
两条都保留，UI 顶部横幅提示「有 1 个冲突待处理」，点击进入对比合并界面。

### 5.3 不同 kind 的合并策略

| kind | 合并方式 | 理由 |
|---|---|---|
| note / thought / diary | 行级三方合并 | 文本，可自动合并 |
| diary_ai | LWW（整体替换） | AI 生成物，无需合并 |
| bookmark | meta 字段级合并 + 正文层 LWW | 归档内容是派生的 |
| **credential** | **不合并，LWW + 保留旧值副本** | 密码字段合并无意义且危险 |

**credential 特殊规则**：任何冲突都生成「旧版本副本」，绝不尝试合并密码字段。

## 6. 墓碑与回收站

### 6.1 墓碑

```json
// /vault/tombstones/<hmac>.enc  (解密后)
{ "id": "uuid", "deleted_at": 1731052800000, "device_id": "devA", "rev": 5 }
```

- **TTL 90 天**，超过则物理删除墓碑文件（避免无限增长）
- 本地需维护墓碑索引，避免每次同步都拉全部墓碑（用 `sync_state` 的 etag 判断）
- 删除顺序：**先写墓碑 → 再 DELETE 条目文件**。反了会导致其他设备先看到文件消失、无法判断是删除还是同步故障

### 6.2 回收站

| 项 | 规则 |
|---|---|
| 保留期 | 30 天 |
| 存储 | 本地 `trash` 表，完整加密快照 |
| 云端 | 只留墓碑，不留正文（省空间） |
| 恢复 | 恢复到本地 → 生成新 oplog（op=restore）→ 推送 |
| 清空 | 物理删除本地 + 确保墓碑已写 |

## 7. 错误分类与处理

| 错误码 | 触发 | 处理 | 用户可见提示 |
|---|---|---|---|
| `E_AUTH` | 401 / 403 | 停止同步，禁用自动重试 | 「WebDAV 认证失败，请检查用户名或应用密码」 |
| `E_NET` | 超时 / DNS / 连接失败 | 退避重试（1s→2s→4s→…→5min） | 「网络不可用，将在恢复后自动同步」 |
| `E_RATE` | 429 / 503 | 长退避（30s→1min→5min→10min），单次请求数减半 | 「服务端限流中，稍后重试」 |
| `E_QUOTA` | 507 | 停止上传，提示清理 | 「云端空间不足，请清理快照或扩容」 |
| `E_CONFLICT` | 412 | 重新拉取并合并，最多 3 轮 | 静默（超过 3 轮才提示） |
| `E_CORRUPT` | 解密失败 / hash 不匹配 | **隔离不覆盖**，跳过该条 | 「有 1 个文件损坏，已隔离，请检查」 |
| `E_VAULT_MISMATCH` | vault_id 不符 | 拒绝同步 | 「该目录属于另一个资料库，请确认」 |
| `E_SCHEMA_TOO_NEW` | 云端 schema 更高 | 拒绝同步 | 「请升级 App 后再同步」 |
| `E_PATH` | 404 / 409（目录不存在） | 自动 MKCOL 重建目录后重试 | 静默 |

**隔离机制**：解密失败的文件不删除、不覆盖，移动到本地 `quarantine/<path>`，
并在「同步诊断」页列出，供用户手动处理或提交反馈。**这是防数据丢失的最后一道闸。**

## 8. 特殊场景

### 8.1 首次绑定已有 vault（新设备）

```
1. 用户输入 WebDAV 地址 + 账号 + 应用密码
2. GET /vault/meta.enc → 存在？
   - 不存在 → 创建新 vault（生成 DEK、恢复码）
   - 存在 → 要求输入主密码或恢复码 → 解包 DEK → 校验
3. 本地已有数据？
   - 否 → 全量下载（分批 50 条，可中断续跑）
   - 是 → 弹窗三选一：
       [合并（推荐）] 重复 id 走冲突规则，不同 id 全部保留
       [以云端为准]   本地数据先备份到 trash 再覆盖
       [以本地为准]   云端数据先下载到 quarantine 再覆盖（需二次确认）
4. 下载完成后重建 FTS + 向量索引（后台任务）
```

### 8.2 首次同步（云端为空）

分批上传：每批 50 条，`If-None-Match: *`。中断后从 `oplog.applied=0` 继续，天然幂等。

### 8.3 离线编辑后上线

`oplog` 堆积 → 上线后按 seq 顺序推送。若某条遇到 412 → 走合并 → 合并结果作为**新的 oplog 记录**追加，
原记录标记 `applied=1`（已处理），不删除。这样审计链完整。

### 8.4 同步过程中 App 被杀

所有写操作在事务内，oplog 与实体要么同时成功要么同时失败。
重启后：`oplog.applied=0` 的就是待推送，`sync_state` 就是已确认的远端状态。**无需额外恢复逻辑。**

## 10. 请求预算与限流

```
单次同步请求预算：200
  - L1 探测          1
  - L2 发现          1 或 16
  - 墓碑             ≤ 5
  - meta             1
  - 条目拉取          ≤ 100
  - 推送             ≤ 60
  - 校验             ≤ 10
超出预算 → 保存进度，下次续跑（分片游标落库）
```

**并发度**：全局最多 3 个并发 HTTP 请求。串行队列保证不会瞬时打满服务商限制。

**退避策略**：

| 错误 | 首次等待 | 倍率 | 上限 |
|---|---|---|---|
| E_NET | 1s | ×2 | 5min |
| E_RATE | 30s | ×2 | 10min |

## 11. UI 状态映射

同步状态必须对用户可见，但不能打扰：

| 内部状态 | UI 表现 |
|---|---|
| IDLE（已同步） | 顶部无提示 |
| PROBE / DISCOVER / PULL | 顶部细进度条 + 「同步中…」 |
| PUSH | 「正在上传 3 项…」 |
| 有冲突 | 橙色横幅「有 1 个冲突待处理」，点击进入合并 |
| BACKOFF | 静默，仅在设置页显示下次重试时间 |
| FAILED(E_AUTH) | 红色横幅「WebDAV 认证失败」，点击跳设置 |
| FAILED(E_QUOTA) | 橙色横幅「云端空间不足」 |
| 有隔离文件 | 设置页「同步诊断」内红点提示 |

## 12. 与其它子系统的接口

| 接口 | 方向 | 说明 |
|---|---|---|
| `WriteGateway.write()` → `SyncScheduler.kick()` | Storage → Sync | 写入后 debounce 8s 触发 |
| `SyncEngine` → `EmbeddingQueue.enqueue()` | Sync → Retrieval | 远端拉取的新条目需要向量化 |
| `SyncEngine` → `ArchiveService.onEntrySynced()` | Sync → Archive | 远端新书签按策略归档 |
| `SyncEngine` → `AgentActivity.log()` | Sync → Agent | 记录同步事件（不进日总结，仅诊断） |
| `SyncEngine` ← `CapabilityDetector` | Sync ← WebDAV | 服务器能力探测结果 |

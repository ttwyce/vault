# 05 · 网页归档子系统

## 1. 要解决的两个问题（必须分开设计）

| 问题 | 用户感受 | 技术本质 |
|---|---|---|
| **P1 链接失效** | 「收藏了打不开」 | 站点关停、404、被墙、域名过期 |
| **P2 内容变更** | 「我记得不是这么写的」 | 页面被编辑、删除、改版 |

两者的解法不同：

- P1 → 归档内容必须**自包含**，不依赖原站；辅以 Wayback Machine 兜底
- P2 → 需要**多版本快照** + 变更对比

## 2. 三层归档模型

Flutter 三端都没有无头浏览器，做不到 SingleFile 那种像素级保真。所以做**三层降级**：

| 层 | 内容 | 体积 | 用途 | 是否必存 |
|---|---|---|---|---|
| **L1 正文层** | 提取后的 Markdown + 本地化图片 | 50~300 KB | 全文检索、向量检索、AI 输入、离线阅读 | **必须** |
| **L2 快照层** | PDF（保排版） | 100 KB~2 MB | 「原站打不开时仍能看到原貌」 | 按策略 |
| **L3 原始层** | 原始 HTML + 内联资源 | 0.5~5 MB | 日后重新提取、调试、深度取证 | 可选 |

**L1 必须无条件保存**。理由：它是检索和 AI 的唯一输入源。省掉 L1，「找回」功能直接废掉，
而它只有几十 KB，1000 条也才 200MB。

**L2 是解决 P1 的主力**。三端都能生成 PDF，且 PDF 自包含、体积可控、可长期保存。

## 3. 剪藏入口（决定日活）

| 平台 | 入口 | 实现 |
|---|---|---|
| Android | 系统分享菜单 | `receive_sharing_intent` 接收 `text/plain`（URL）；可选 `ACTION_SEND` 原生通道 |
| Android | 长按悬浮球 / 快捷磁贴 | 前台服务 + 悬浮窗（可选，二期） |
| iOS | Share Extension | **必须写原生 Swift**，通过 App Group 把 URL 传给主 App |
| iOS | 复制链接后自动识别 | 监听剪贴板（需用户允许），App 前台时提示「是否归档该链接？」 |
| Windows | 全局热键（默认 `Ctrl+Shift+V`） | `hotkey_manager` + 托盘常驻 |
| Windows | 剪贴板监听 | 检测到 URL 时托盘气泡提示 |
| 三端 | App 内粘贴 | 输入框粘贴 URL 直接归档 |

**体验要求**：从分享到「归档完成」≤ 3 秒（只存 L1），L2 后台异步生成，生成完推送通知。

## 4. 抓取流水线

```
URL 入队
  → 1. 去重检查（同 URL 已有？→ 提示「已归档过，是否更新快照」）
  → 2. 元数据抓取（HEAD/GET，拿 status / content-type / title / favicon）
  → 3. 加载页面（WebView 隐藏加载，等待 networkIdle + 500ms）
  → 4. 注入 readability.js → 提取正文 HTML
  → 5. HTML → Markdown，图片下载并改写为本地引用
  → 6. 生成 L2 PDF（按策略）
  → 7. 保存 L3 原始 HTML（按策略）
  → 8. 写 blob_ref + 计算 hash → 入同步队列
  → 9. 入向量化队列
```

### 4.1 提取细节

| 项 | 规则 |
|---|---|
| 正文容器 | readability 的 `article.content`；失败则退化为 `<body>` 全文 |
| 图片 | 只保留 `width ≥ 200` 或 `height ≥ 200` 的；下载失败保留原 URL 并标注 |
| 懒加载 | 提取前滚动到底部触发 `IntersectionObserver`，等待 1s |
| 反爬页面 | 检测到「请开启 JavaScript」「验证中」等特征 → 标记 `archive_status = blocked`，只存元数据 |
| 付费墙 | 检测常见 paywall 类名 → 标记并提示用户 |
| 超时 | 单页 20s，超时降级为「仅元数据 + 原文 HTML（不渲染）」 |

### 4.2 存储映射

```
entry (kind=5, meta.url, meta.site, meta.archive_status)
  └── blob_ref:
        kind=1 (text)   → blobs/xx/<hash>.bin   ← L1 正文 Markdown
        kind=2 (pdf)    → blobs/xx/<hash>.bin   ← L2
        kind=3 (html)   → blobs/xx/<hash>.bin   ← L3
        kind=4 (image)  → blobs/xx/<hash>.bin   ← 正文图片（多条）
        kind=5 (favicon)→ blobs/xx/<hash>.bin
```

`meta.archive_status` 枚举：`none` / `metadata` / `text` / `full` / `blocked` / `paywalled` / `dead`

## 5. 归档策略引擎

### 5.1 三级策略

| 模式 | 存什么 | 触发方式 | 体积 |
|---|---|---|---|
| `link` | 仅 URL + 标题 + 元数据 | 手动选 | ~1 KB |
| `text` | + L1 正文 | **默认，自动** | 50~300 KB |
| `full` | + L2 PDF + L3 HTML | 手动 或 定时 | 1~5 MB |

### 5.2 全局配置

```
自动正文归档：   始终开启（不可关，L1 是检索基础）
自动完整快照：   关闭（默认）/ 每次剪藏 / 每日 02:00 / 每周日 02:00
快照保留期：     30 天 / 1 年 / 永久（默认 1 年）
云端配额上限：   默认 = WebDAV 剩余空间 × 80%
超配额策略：     按 LRU 把最老的 L2/L3 降级为「仅云端」或删除
快照同步：       全部设备 / 按需下载（默认）
```

### 5.3 定时任务的平台现实

| 平台 | 可靠性 | 方案 | 文案 |
|---|---|---|---|
| Windows | 高 | 托盘常驻 + 定时器 | 「每天 02:00 自动归档」 |
| Android | 中 | `workmanager`（受 Doze 影响） | 「App 运行时自动归档」 |
| iOS | 低 | BGTaskScheduler 额度极少 + 前台补偿 | 「下次打开 App 时归档」 |

**不要承诺「后台自动」**。所有平台统一策略：**前台补偿 + 启动时检查积压任务**。

### 5.4 配额守卫

```
每次归档 L2/L3 前：
  if 云端已用 + 预计体积 > 配额上限:
     按 created_at 升序，把最老的 full 降级为 text（删除 L2/L3 blob）
     if 仍不够 → 拒绝本次 L2/L3，只存 L1，并提示用户
```

## 6. 死链与内容变更检测

### 6.1 死链检测

```
任务：每周一次（Windows）/ 每月一次（移动端），批量 HEAD 检查
  → 200/301/302  → 存活，记录最终 URL
  → 404/410      → 标记 dead
  → 超时/DNS失败 → 标记 unreachable（重试 2 次后）
  → 403/451      → 标记 restricted（可能是反爬，不算死链）
```

**死链的 UI 处理**：

- 列表项显示灰色 + 「原站已失效」标签
- 点开直接展示 L2 PDF 快照（若有），否则展示 L1 正文
- 提供「尝试从 Wayback Machine 找回」按钮：

```
GET https://archive.org/wayback/available?url=<url>
  → 有快照 → 提示「已找到 2019-03-12 的存档版本」→ 打开 archive.org 链接
  → 无快照 → 提示「建议手动提交到 archive.org」
```

### 6.2 内容变更检测

```
任务：对标记了「关注变更」的条目，每月重新抓取 L1
  → 计算 simhash(新正文) vs simhash(旧正文)
  → 相似度 < 0.9 → 提示「这页内容有变化」
  → 保留旧版为 history（可对比查看）
```

**成本控制**：默认只对「用户手动标记」或「30 天内访问过」的条目做变更检测，避免全库重抓。

### 6.3 自动提交存档（可选功能）

归档时可选勾选「同时提交到 Internet Archive」，调用 Save Page Now API。
默认关闭（涉及把 URL 发送给第三方）。

## 7. 按需下载（关键，别漏）

`blobs/` **默认不同步到所有设备**。这是同步能否长期可用的决定因素。

```
本地状态：blob_ref.local = 0（仅云端）/ 1（本地已有）

列表页：不请求 blob，只显示标题 + 摘要 + 归档状态徽章
点开阅读：
  1. 需要 L1 正文 → 若 local=0，显示骨架屏 + 下载（通常 <100KB，秒开）
  2. 需要 L2 PDF → 用户点「查看原貌」才下载，带进度条
  3. 下载完成 → local=1，写入本地缓存
```

**缓存清理**：本地 blob 缓存上限（默认 500MB），超出按 LRU 清理，
清理时只置 `local=0`，**不删云端**。

## 8. PDF 生成的三端实现

| 平台 | 方案 | 风险 |
|---|---|---|
| iOS | `WKWebView.createPDF(configuration:)` → Data | 低，系统原生 API |
| Android | WebView `draw()` 到 `android.graphics.pdf.PdfDocument`，手动分页 | 中，长页面分页需自己算 |
| Windows | WebView2 `PrintToPdfAsync` | **高**，依赖 WebView2 封装成熟度 |

**Android 分页要点**：按 A4 比例（595×842 pt @72dpi）计算可视高度，
逐页 `canvas.translate(0, -pageHeight * i)` 后 `webView.draw(canvas)`。

**降级路径**（任一平台 PDF 失败时）：

1. 尝试平台原生方案
2. 失败 → 用 `pdf` 包 + `printing` 包，把 L1 Markdown 渲染成简易 PDF（不保真但可用）
3. 再失败 → 只保留 L1 + L3，标记 `archive_status = text`，UI 提示「未能生成完整快照」

**验收标准**：三个平台对同一篇文章生成的 PDF，正文内容完整可读（不要求像素一致）。

## 9. 阅读器设计

| 模式 | 内容 | 场景 |
|---|---|---|
| 纯净模式（默认） | L1 Markdown 渲染 | 日常阅读、手机端 |
| 原貌模式 | L2 PDF | 需要看图表、排版时 |
| 对比模式 | 新旧两版 L1 并排 diff | 内容变更提示后 |

阅读器必须支持：高亮标注（写入 `meta.highlights`）、划词 → 「问 AI」、
底部显示「归档于 2026-11-08 · 原站状态：存活」。

## 10. 数据结构补充

```json
// entry.meta（kind=5 bookmark）
{
  "url": "https://example.com/post/123",
  "final_url": "https://example.com/post/123?utm=xx",
  "site": "example.com",
  "author": "…",
  "published_at": 1730000000000,
  "archive_status": "full",
  "archive_policy": "text",
  "last_checked_at": 1731052800000,
  "http_status": 200,
  "watch_changes": false,
  "reading_time_min": 8,
  "highlights": [{ "text": "…", "offset": 1024, "note": "…" }],
  "excerpt": "前 200 字摘要（用于列表展示，避免读 blob）"
}
```

**`excerpt` 字段很重要**：列表页展示摘要时不能去读 blob（否则每屏几十次 IO），
所以要在归档时就把前 200 字存进 meta。

## 11. 验收标准

| # | 标准 |
|---|---|
| A1 | 三端分享入口均可在 3 秒内完成 L1 归档 |
| A2 | 原站关停后，条目仍可离线阅读完整正文 |
| A3 | L2 PDF 在 Android / iOS / Windows 均可生成且内容完整 |
| A4 | 1000 条归档后，同步耗时不超过基线的 1.5 倍（证明 blob 未全量同步） |
| A5 | 配额超限时能自动降级，不出现同步失败 |
| A6 | 死链检测能正确区分 dead / restricted / unreachable |
| A7 | 归档内容可被全文检索与语义检索命中 |

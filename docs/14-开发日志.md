### 踩到的坑

**① `flutter test` 其实能跑 —— Day 1 的结论是错的**

不是"沙箱禁止本地回环"。真实原因是环境里有 `http_proxy=http://127.0.0.1:51096`，
`flutter_tester` 启动时用本地 WebSocket 回连测试进程，被代理拦下
（`Invalid WebSocket upgrade request`）。设 `NO_PROXY` 后 15 条测试全绿。

**这条要记牢：以后所有 flutter 命令都带上 NO_PROXY。**

**② `file_picker` 13.x 与教程里的 8.x 是两个 API**

```dart
// 8.x
final result = await FilePicker.platform.pickFiles(allowMultiple: true);
if (result != null) { ... result.files ... }

// 13.x：没有 .platform，没有 allowMultiple，直接返回 List
final List<PlatformFile> picked = await FilePicker.pickFiles();
for (final f in picked) { f.name; await f.readAsBytes(); }
```

顺带发现 `PlatformFile.path` 在 Android 的 `content://` 下是 null，
所以导入管线改成「名字 + 读字节的闭包」（`FontImportSource`），core 层不依赖 file_picker。

**③ 不能用 `FileType.custom` + `allowedExtensions`**

`ttf` 在很多 Android ROM 上没注册 MIME，选择器会直接变灰或返回空。
改成 `FileType.any` + 字节校验 —— 反正最终都要校验文件头。

**④ `FontLoader` 只能加不能卸**

同一家族名重复 `load()` 抛异常。所以导入字体的家族名必须由内容哈希生成，
且用 `_loaded` + `_inflight` 双重去重。

**⑤ `VaultApp` 开始依赖字体服务，测试要绕开平台通道**

`FontService.boot()` 需要 path_provider。widget 测试改成直接 pump `AppShell` +
`SketchTheme.light`，验证的仍然是真实路径。

**⑥ 侧栏只有图标，`find.text('记录')` 找不到**

原测试在 1280 宽下走 rail 分支，rail 是纯图标 + Tooltip。
改用 `find.byTooltip(label)`，并补了一条 390 宽的移动端用例。

## 2026-11-08 · Day 3：三个同步前置原语

数据库层要开工前，有三个东西**每一张表都要用**，先把它们做掉并测透，
比先铺 20 张表的 drift 定义划算得多 —— 因为它们的错误会在同步阶段才爆发，
那时候排查成本高一个数量级。

### 1. `UuidV7`（`lib/core/identity/uuid_v7.dart`）

主键用 v7 而不是 v4：**id 序 = 创建序**。

- 同步时按 id 排序等于按创建时间排序，分片目录内的遍历游标可以直接用 id
- 同一毫秒内用 12 位计数器（`rand_a`）保证单调，连续建 1000 条笔记顺序不乱
- 计数器溢出（> 4095）借下一毫秒 —— 宁可 id 比真实时间晚 1ms，也不能乱序
- 附带 `timestampOf()`：能从 id 反解创建时间，同步时做"远端是否更新"的快速判断

### 2. `Hlc` / `HlcClock`（`lib/core/sync/hlc.dart`）

**这是整个同步引擎的地基。** 用墙上时间判断"谁更新"会直接丢数据：
Windows 差几秒、手机飞行模式回来差十几分钟，都会让新修改被旧版本覆盖。

编码 `0000018F2A3B4C5D:0003:devA`（16 位毫秒 + 4 位计数器 + 节点），
**固定宽度**所以字符串比较 == 时间比较 —— 这条如果不成立，
所有"按 hlc 排序取最新"的查询都会错，而且错得很隐蔽。

三个必须守住的点：

| 点 | 为什么 |
|---|---|
| `tick()` 同毫秒递增 | 否则同一毫秒的两次编辑顺序不确定 |
| `observe(remote)` 后本地严格大于远端 | 因果顺序不被时钟漂移破坏 |
| `restore()` 只能前进 | 重启后从零开始会生成比历史更小的时钟值 → 旧版覆盖新版 |

### 3. `Canonical`（`lib/core/crypto/canonical.dart`）

`content_hash` 要在**不同设备、不同 Dart 版本、不同 Map 插入顺序**下算出同一个值。
`jsonEncode(map)` 不满足：Dart 的 Map 迭代顺序取决于构造方式。

三条规则：对象键字典序升序 + 无空白；数组保持顺序；整数值的 `double` 退化成整数形式
（否则 `1.0` 和 `1` 算出两个哈希）。

### 测试

新增 `test/core_primitives_test.dart` 共 22 条，覆盖：

- UUIDv7：格式/版本位/变体位、时间反解、同毫秒单调 500 条、跨毫秒单调、
  计数器溢出 5000 条不回退、非法输入
- HLC：固定宽度编码、编解码往返、同毫秒递增、物理时钟前进归零、
  `observe` 后严格大于远端（模拟 10 分钟时钟漂移）、`observe` 不回退、
  `restore` 只能前进、计数器溢出借毫秒
- Canonical：键序无关、嵌套排序、`1` == `1.0`、字段顺序无关的哈希、
  改一个空格哈希就变、中文与转义稳定、NaN/Infinity 报错

## 2026-11-08 · Day 4：数据库加密定案（A1 假设验证通过）

### 背景

Day 1 的判断是「`sqlcipher_flutter_libs` 已 EOL ⇒ 要走自建构建，成本高」，
所以一直在 A（自编译 SQLCipher）和 B（应用层字段加密 + 明文索引）之间摇摆。

**这个判断也是错的。** 去翻 `sqlite3` 3.9 的构建钩子源码
（`lib/src/hook/compile/description.dart`）才发现：它把「用哪套预编译产物」做成了
一等公民的 user define，SQLCipher 是**内置选项之一**。

### 结论：一行配置

```yaml
hooks:
  user_defines:
    sqlite3:
      source: sqlcipher
```

预编译产物覆盖 Android（arm/arm64/ia32/x64）、iOS（arm64 + simulator）、
Windows（x64/ia32/arm64）。**不需要构建脚本、不需要 CI 矩阵、不需要 vendored 二进制。**

原估 5+ 人日的「自建构建」实际成本 **≈ 0.5 人日**。

### 实测（`test/sqlcipher_probe_test.dart`，6 条用例）

| 验证项 | 结果 |
|---|---|
| `PRAGMA cipher_version` | `4.20.0 community` |
| 错误密钥打开已加密库 | `hmac check failed for pgno=1` → 抛错，符合预期 |
| FTS5 建表 + 中英文查询 | 通过 |
| WAL + 200 行写入 | 通过 |

### 顺带推翻的第二个错误结论

原 06 文档写「FTS5 的 `unicode61` 对中文按字切分，召回率高但精度低」。
实测：**`unicode61` 把连续汉字当成一个 token**，所以

```sql
-- 表里存的是 'WebDAV 增量同步'
SELECT * FROM fts WHERE fts MATCH '同步';   -- 0 条
```

不是精度低，是**完全搜不到**。如果不做这条实测，等做到 M2 全文检索才会发现，
那时候索引格式已经定下来了。

三种方案都试了：

| 方案 | 「同步」 | 「增量同步」 | 结论 |
|---|---|---|---|
| `unicode61` 原样 | 0 | 0 | 不可用 |
| `trigram` 内建 | 0（要求 ≥3 字符） | 1 | 不可单独用 |
| **按字切分 + 短语查询** | **1** | **1** | **采用** |

关键细节：查询必须用**短语**（`MATCH '"同 步"'`），否则两个独立 token 会 OR 起来，
`同步删除` 这种跨词组合也会误命中。已在测试里锁死这条语义。

### 为什么最终选 A 而不是 B

不是「A 更安全一点」，而是 **B 有一个不可修补的洞**：

`entry_fts` 存的是正文的 token 流，`entry_history` / `trash` / `activity` 也都含明文。
拿到 db 文件（iCloud 备份、越狱、取证镜像、备份排除规则写错）就能还原全部内容 ——
对一个卖点是「数据在我手里」、且存密码的产品，这是不能接受的。

B 也不是白做：**字段级 AEAD 是同步层的必需品**（上传到 WebDAV 的每条 item 独立加密），
它和「本地库是否整库加密」是两个层，两件都要做。

### 踩到的三个坑

**① `PRAGMA key = x'..'` 是语法错误**

```
SqliteException(1): near "x'1c65be...'": syntax error
```

SQLite 的 PRAGMA 解析器不接受裸 blob 字面量。SQLCipher 的约定是
**把整个 `x'..'` 当成一个字符串传进去**，由它自己解析成字节：

```dart
'PRAGMA key = "x\'$hex\'";'   // 外层双引号不能省
```

**② 只查 `cipher_version` 根本发现不了"忘了加密"**（这条最要命）

我原本的断言是 `PRAGMA cipher_version` 非空。写测试时才发现它形同虚设：

本项目全局用 SQLCipher（`source: sqlcipher`），所以**任何**连接都能报出版本号，
包括那条忘了执行 `PRAGMA key` 的连接。测试里 `VaultDatabase(NativeDatabase.memory())`
直接构造、没设 key，断言竟然通过了 —— 数据库以明文建出来，一切正常。

实测找到了真正的探针：`PRAGMA cipher_salt`

```
noKey   → 0 行
withKey → 1 行，a018bbf118e28d1841421538c50273c6
```

没有密钥上下文时 salt 为空。于是改成两条断言，并加第三道文件级校验
（落盘后文件头不能是 `SQLite format 3\0`）。

> 这是整个项目里唯一一种"无声失效"的失败方式：不报错、测试全绿、
> 上线后密码明文躺在磁盘上。所以它进了 README 的工程红线。

**③ `drift` 自己就导出一个 `DatabaseOpener`**

命名冲突。改名 `VaultDatabaseOpener`。同理 `drift` 导出 `isNotNull`，
测试里要 `import 'package:drift/drift.dart' hide isNotNull;`。

| `vault_lock.dart` | 创建 / 解锁 / 改密码 / 重置恢复码 |

**2. 加密依赖收敛到一个包**

原计划 `sodium_libs` + `cryptography` 两个包。实测 `cryptography` 2.9 同时提供
XChaCha20-Poly1305、Argon2id、HKDF，于是全部走它 —— 少一套原生依赖就少三端
各一次的构建与兼容验证。详见 02 §13。

**3. Argon2id 实测：2.1 秒，不是文档写的 0.6~1.2 秒**

`test/kdf_perf_probe_test.dart`（桌面 JIT，`flutter_tester`）：

| 参数 | 耗时 |
|---|---|
| m=19MB, t=2, p=1（OWASP 最低线） | 606 ms |
| m=32MB, t=3, p=4 | 1,224 ms |
| **m=64MB, t=3, p=4（采用）** | **2,147 ms** |

`cryptography` 的 Argon2id 是**纯 Dart 实现**（会起 isolate 并行，但每 lane 仍是
Dart 代码），吞吐只有 C 实现的 1/3~1/5。设计阶段的"0.6~1.2s"是凭 C 实现经验推的。

**仍然保留 64MB**：这是密码管理器品类的行业基线（Bitwarden 默认就是
`m=64MB t=3 p=4`），低于它要在安全审计上多解释。但换来三条硬性 UX 要求：
解锁页必须有进度、派生不阻塞首帧、必须提供生物识别/短期免密。
已作为 R19 记入风险表，**真机数据出来后回填**。

**4. 恢复码：24 词 BIP-39，校验和是核心**

不自己造词表，理由是校验和：24 词的最后 8 bit 是前 256 bit 的 SHA-256，
抄错一个词在**设置当下**就能发现。没有校验和，手抄错误完全无法检测。

四组官方向量都用独立 Python 实现（hashlib + 手工 11 位切分）复算过才写进测试，
不是凭记忆。

**5. 恢复码不跑 Argon2**

256 bit 真随机熵没有可爆破空间，慢哈希的安全增益是零，代价却是
"灾难恢复时在陌生设备上多等 2 秒，还可能内存不足失败"。所以走 HKDF（微秒级）。

### 踩到的坑

**① `SecretKey` 没有 `.bytes`**

`cryptography` 的 `KdfAlgorithm.deriveKey` 返回 `SecretKey` 而不是 `SecretKeyData`，
要 `await key.extractBytes()`。HKDF 的 `deriveKey` 返回 `SecretKeyData`，
但它的 `.bytes` 是 `List<int>`，喂给 `Uint8List` 参数前必须 `Uint8List.fromList`。

**② HKDF 没有同步接口**

文档里提到 `DartArgon2id` 有同步版，但 `DartHkdf` 只有 `Future`。原本想用
`toSync().deriveKeySync()` 省一次 microtask，编译不过 —— `KdfAlgorithm` 上没有
`toSync`。改成 async 即可，反正只调一次。

**③ 指纹原本在泄露密钥字节**

`SecretBytes.fingerprint` 第一版取首尾各 4 字节，测试断言
"toString 不包含 ababab" 直接挂了 —— 因为密钥全 0xAB 时指纹就是 `abababab`。

这不是测试写错，是**实现有问题**：把 64 bit 真实密钥写进日志。虽然剩余 2^192
空间仍不可爆破，但"日志里出现密钥材料"本身就不该开这个先例。

改成 `sha256(key)` 前 4 字节：不含任何密钥信息，仍保持可比性。
测试补了两条断言：指纹不能是 `toHex()` 的子串、改一个字节指纹必须全变。

**④ `RecoveryCode.parse` 自己就验校验和**

原本想写"缩写还原后校验和不匹配"的用例，结果 `parse` 内部已经验了，
直接抛异常，`code` 变量根本没赋上。改成用真实生成的码做全词缩写往返。

**⑤ 3 字母前缀：`leg` 是词，`sol` 不是**

`leg` 本身在词表里，所以 `_resolve('leg')` 走精确匹配成功；而 `sol` 不是词，
是 solar/soldier/solid/solution/solve 的公共前缀。测"歧义前缀被拒"必须用 `sol`。
规则是：**精确匹配优先，其次才按 4 字母以上前缀补全**。

## 2026-11-08 · Day 7：唯一写入口 + 活动埋点

### 已完成

**1. `WriteGateway`（`lib/data/write/`，3 个文件）**

全项目唯一的写入入口。一次写入在**同一个事务**里做八件事：

```
① 读旧状态（算 rev / base）
② 旧状态归档进 entry_history（三方合并的 base）
③ 新状态封进 ItemEnvelope（加密）
④ 写 oplog（outbox）
⑤ 改 entry
⑥ 更新 FTS 索引
⑦ 回收站增删
⑧ 持久化 HLC
```

绕过它直接 `db.into(entries).insert()` 的后果很具体：那条变更永远
不会被推送，用户换设备时才发现"这条笔记只有手机上有"，而且无法事后修复
—— 本地有数据，但没有推送记录，不知道要推什么。

**2. 条目加密信封（`ItemEnvelope`）**

本轮唯一一个"做错了要重新加密全库"的决定。原方案 `AAD = entity + id + rev`
有个死循环：

> 解密需要 AAD → AAD 需要 rev → rev 在密文里 → 解不开。

三条出路：AAD 只绑 id（丢掉防重放）、rev 进文件名（改名破坏 If-Match）、
**明文头携带 {entity,id,rev} 且 AAD = 头部字节本身**。

选第三条，还额外买到两样：同步层可以只读头部做冲突预判（不验签不解密）；
**oplog payload 与云端 item 文件字节完全一致**，推送可以直接 PUT。

**3. 活动埋点（`ActivityLogger`）**

按 (kind, entry) 做时间窗口合并，不记流水账：

| 事件 | 窗口 | 语义 |
|---|---|---|
| 浏览 / 归档阅读 | 30 分钟 | 一次阅读会话，dwellMs 累加 |
| 编辑 | 5 分钟 | 一次编辑会话 |
| 搜索 | 60 秒 | 防打字机式刷屏 |
| 创建 / 剪藏 | 不合并 | 独立事件 |

合并后的粒度恰好是日总结要的：「读了 5 篇、写了 3 条、搜了 8 次」，
而不是「点击了 47 次」。`dwellMs` 是这张表最有价值的字段 ——
没有它只能说"你看了 12 篇"，有它才能说"你在 WebDAV 那篇上花了 18 分钟"。

### 踩到的坑

**① `SecretWrapper` 原本只够包密钥**

它接收 `SecretBytes plaintext` 并返回 `Uint8List`，包 32 字节 DEK 正好，
包 KB 级快照就要先把字节塞进 `SecretBytes`（多一次复制）。
泛化成 `seal`/`open`（任意 `List<int>`），`wrap`/`unwrap` 保留给 DEK，
参数 `kek` 改名 `key`。

**② drift 的查询构造器类型是 `$EntriesTable` 不是 `Entry`**

`where((Entry t) => ...)` 编译不过 —— `Entry` 是数据类 `EntryRow` 的旧名字，
表类叫 `$EntriesTable`。直接用类型推断 `where((t) => ...)` 最省事。
`OrderClauseGenerator<Oplog>` 同理，改成 `<OrderClauseGenerator<dynamic>>`。

**③ `getSingle()` 忘了 `limit(1)`**

```dart
db.select(db.oplogs)..orderBy([desc(t.seq)])   // 拿到全部行
  .getSingle()                                  // Bad state: Too many elements
```

三处同样的问题，一次全挂。`orderBy` 不会隐式限行。

**④ `const FormatException('...$rev')` 编译不过**

插值里有局部变量就不是常量表达式。这种地方很容易手滑 —— 分析器报
`Invalid constant value`，定位在字符串那一列，不看行号会以为别处有问题。

**⑤ `SecretBytes.fingerprint` 改成哈希后，DatabaseKey 也要跟着改**

`DatabaseKey` 原来自己实现了 `_hex()` / `_constantTimeEquals`，
和 `SecretBytes` 完全重复。改成委托后少 40 行，且以后只维护一份。

### 踩到的坑

第一版想直接 `return null` 了事。但把"文件损坏"当成"首次使用"是灾难性的：
App 会引导用户新建一个 vault，用户以为自己原来的数据没了，

唯一入口 —— 那等于永久锁死整个库。改成先写 `.tmp` 再 `rename`。

**⑤ `ProviderContainer.dispose()` 不关数据库句柄**

新写的守卫测试全挂在 tearDown：

```
PathAccessException: Deletion failed, path = '...ault_guard_xxx'
(OS Error: 另一个程序正在使用此文件, errno = 32)
```

`dispose()` 只销毁 provider，会话持有的 SQLCipher 文件还开着。

"测试失败"——把断言其实通过的事实完全掩盖掉。

修法：tearDown 里先 `lock()`（它会 close opener）再删目录，并给 3 次重试。

### 三个值得记的判断

**1. 不伪造解锁进度**

用户看到秒数在走就知道没死。

这条规则抽成了纯函数 `resolveGateScreen`，单独有测试。

**3. 抽查恢复码时把词表收起**（onboarding-ui 主动提的）

原本设计是"词表一直显示，下面出 3 个输入框"。代理提出：那样验证就是自欺 ——
用户可以直接往上瞟。改成点「我已抄好」后词表收起、只剩输入框。

这个判断比我原来的设计对。

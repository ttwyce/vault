# 11 · 功能补齐方案

> **DDL 说明**：本文档中的建表语句为便于阅读就地保留，**完整建表脚本以 [13 数据模型总表](13-数据模型总表.md) 为准**。

> 范围：日记页面、笔记分类与标签、归档网站页面、账号分类/自定义字段/备注。
> 原则：**不新增实体类型，全部挂在现有 `entry` 模型上**；新增的只有两张独立同步实体（`category` / `tag`）和一张本地索引表（`diary_index`）。

---

## 0. 总览

| # | 功能 | 新增页面 | 新增数据 | 影响面 |
|---|---|---|---|---|
| 1 | 日记页面 | 日记总览（月历 + 列表）、日记详情（已有 11 屏升级） | `diary_index` 表、`meta.date` | 检索、同步（无变化） |
| 2 | 笔记分类与标签 | 分类与标签管理页、笔记列表左侧加分类树 | `category`、`tag`、`entry_category`、`entry_tag` | **同步引擎需支持新实体** |
| 3 | 归档网站页面 | 归档总览（列表 + 死链 + 存储） | `link_check` 表、`meta` 扩字段 | 归档子系统、配额 |
| 4 | 账号分类/自定义字段/备注 | 账号编辑页、账号详情扩展 | `credential` 独立表扩字段 | 加密边界、AI 可见性 |

**与现有设计的一致性约束**（四条，所有新增功能都必须遵守）：

1. 视觉：手绘草图风 —— 不规则圆角 + 虚线描边 + 硬偏移阴影 + 歪 0.5~0.8deg。
2. 颜色分工：红 `#FF4D4D` 只给「AI 动作 / 当前状态 / 主按钮」，蓝 `#2D5DA1` 只给「旁注 / 链接」。
3. AI 生成的内容必须可识别（便签黄底 + 引用列表），且可溯源。
4. 任何写入操作都要过 `WriteGateway`（先写 oplog 再改实体），同步沿用「永不覆盖 + 冲突副本」规则。

## 1. 日记页面

### 1.1 现状与缺口

现有只有「单日详情」（第 11 屏）。缺的是**入口**：用户没有地方「看我这一个月写了什么」，也无法快速补写漏掉的那天。

### 1.2 页面结构

```
┌──────────────────────────────────────────────────────────────┐
│ 日记                                    2026 年 11 月  ‹ ›   │
├──────────────┬───────────────────────────────────────────────┤
│              │  月历（7 列 × 6 行）                           │
│  年 / 月列表  │  每格：日期 + 内容圆点（实心=有日记，空心=仅AI）│
│              │  今天：实心红块                                │
│  2026        │  点格 → 右侧预览 / 双击 → 进入详情              │
│   11 ✓       │                                               │
│   10         ├───────────────────────────────────────────────┤
│   09         │  本月 8 篇 · 连续 3 天 · 平均 320 字            │
│              │  ┌ 11-08 跟限流较劲的一天  320 字  你写的 ┐     │
│              │  ┌ 11-07 阴天，什么都没干  180 字  你写的 ┐     │
│              │  ┌ 11-06 （AI 生成）      150 字  AI 写的 ┐     │
│              │  └ …                                     ┘     │
└──────────────┴───────────────────────────────────────────────┘
```

**详情页（升级第 11 屏）**：左日历保留，中间是「你写的」，右侧是「AI 日记」。
关键改动：**日期头加一个「补写」按钮**，允许对过去任意一天补写日记（`meta.date` 与 `created_at` 分离）。

### 1.3 数据字段

日记仍然用 `entry`，`kind = 3`（用户）/ `4`（AI）。新增字段全部进 `meta`：

```json
{
  "date": "2026-11-08",          // 归属日期，YYYY-MM-DD，本地时区，不存时间戳
  "weather": "阴",
  "mood": "平静",                 // 可选枚举：平静/好/一般/糟
  "location": null,
  "word_count": 320,
  "backfilled": false            // 是否补写（created_at 晚于 date）
}
```

新增一张**本地索引表**（不同步，可从 entry 重建）：

```sql
CREATE TABLE diary_index (
  date          TEXT PRIMARY KEY,   -- YYYY-MM-DD
  user_entry_id TEXT,               -- kind=3
  ai_entry_id   TEXT,               -- kind=4
  word_count    INTEGER DEFAULT 0,
  has_mood      INTEGER DEFAULT 0
);
CREATE INDEX idx_diary_month ON diary_index(date);
```

> **为什么用 `meta.date` 而不是 `created_at`**：补写、跨时区、以及「凌晨两点写的算前一天」这三件事都要求日期是**显式字段**，不能从时间戳推。

### 1.4 交互方式

| 操作 | 行为 |
|---|---|
| 打开日记 Tab | 默认定位到今天所在的月份 |
| 点月历某一格 | 右侧预览该日日记（若有）；空格显示「这天还没写」+ 补写按钮 |
| 双击格子 | 进入详情编辑 |
| 「写今天的」 | 全局快捷键 `⌘⇧D`，直接进当天详情并聚焦正文 |
| 切月 | 左右箭头 / 触控板横扫 / `←→` |
| AI 日记 | 每天 23:50 自动生成；未生成时格子显示空心圆；可手动「现在生成」 |
| 连续天数 | 底部显示「连续 3 天」，断签变灰，不弹提醒（不做打卡压迫感） |

### 1.5 实现范围

| 一期 | 二期 |
|---|---|
| 月历 + 列表 + 详情 + 补写 + 天气/心情 | 日记模板、年度回顾、导出为 PDF 手账、语音转日记 |

**不做**：打卡提醒、连续天数排行榜、社交分享。理由：这个产品是「自己的档案馆」，不是习惯养成工具。

## 2. 笔记分类与标签

### 2.1 核心设计决策：分类和标签分工

这是最容易做坏的一处。规则定死：

| | 分类 Category | 标签 Tag |
|---|---|---|
| 数量 | 一条笔记**最多 1 个** | 一条笔记**可以多个**（≤ 8） |
| 结构 | **两级树**（父/子），不允许三级 | 扁平，无层级 |
| 谁创建 | 用户手动建 | 用户建 + AI 建议 |
| 用途 | **归属**（这东西属于哪个项目/领域） | **横切**（这东西涉及什么主题） |
| 删除 | 删分类 → 条目回到「未分类」，不删条目 | 删标签 → 只解除关联 |
| 同步冲突 | LWW + 同名合并 | LWW + 同名合并，取 usage 大的 |

**一条硬规则**：分类是树，标签是云。不要给标签加层级，也不要让一条笔记属于多个分类 —— 这两件事一放开，用户就会陷入「整理瘫痪」，而 AI 也失去了「该放哪」的判断依据。

### 2.2 页面结构

**A. 笔记列表（升级第 08 屏）左侧栏**

```
┌────────────────────┐
│ 搜一搜…            │
├────────────────────┤
│ 全部          134  │
│ 未分类         12  │
├────────────────────┤
│ 分类           ＋  │
│  ▾ 工作        48  │
│     项目 A     21  │
│     项目 B     14  │
│  ▸ 学习        36  │
│  ▸ 生活        22  │
├────────────────────┤
│ 标签           管理│
│ # webdav      ×6   │
│ # 同步        ×4   │
│ # 设计        ×2   │
└────────────────────┘
```

**B. 分类与标签管理页（新增第 15 屏）**

```
┌──────────────────────────────────────────────────────────────┐
│ 分类与标签                          [＋ 新建分类] [＋ 新建标签]│
├──────────────────────────┬───────────────────────────────────┤
│ 分类（拖拽排序 / 改层级）  │ 标签（按使用次数）                 │
│  ▾ 工作            48     │  ● #webdav     6 条   改名 · 合并  │
│     项目 A         21     │  ● #同步       4 条   改名 · 合并  │
│     项目 B         14     │  ● #设计       2 条   改名 · 合并  │
│  ▸ 学习            36     │  ● #flutter    1 条                │
│  ▸ 生活            22     │                                   │
│  ＋ 新建子分类             │  ⚠ 有 2 组标签可能重复，建议合并    │
└──────────────────────────┴───────────────────────────────────┘
```

### 2.3 数据字段

```sql
-- 分类：树形，两级
CREATE TABLE category (
  id          TEXT PRIMARY KEY,      -- uuid
  kind        INTEGER NOT NULL,      -- 归属类型：1笔记 2想法 3日记 5归档 6密码
  parent_id   TEXT,                  -- NULL = 一级；非空 = 二级（禁止三级）
  name        TEXT NOT NULL,         -- 明文（受 SQLCipher 保护）
  color       TEXT,                  -- 可选，仅用于列表左侧小圆点
  icon        TEXT,                  -- 可选，Lucide 图标名
  sort_order  INTEGER NOT NULL DEFAULT 0,
  entry_count INTEGER NOT NULL DEFAULT 0,   -- 冗余计数，异步更新
  created_at  INTEGER, updated_at INTEGER,
  hlc         TEXT NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_cat_kind ON category(kind, parent_id, sort_order);

-- 标签：全局共享，跨 kind
CREATE TABLE tag (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,         -- 唯一（deleted=0 时）
  color       TEXT,
  usage_count INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER, updated_at INTEGER,
  hlc         TEXT NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX idx_tag_name ON tag(name) WHERE deleted = 0;

-- 关联
CREATE TABLE entry_category (
  entry_id TEXT NOT NULL, category_id TEXT NOT NULL,
  PRIMARY KEY (entry_id, category_id)
);
CREATE TABLE entry_tag (
  entry_id TEXT NOT NULL, tag_id TEXT NOT NULL,
  PRIMARY KEY (entry_id, tag_id)
);
```

`entry.meta` 不存分类/标签（避免双写不一致），一律走关联表。

### 2.4 同步影响（这是本次唯一需要改同步引擎的地方）

`category` / `tag` 是**独立同步实体**，不能塞进 entry：

- 云端路径：`/vault/taxonomy/<hmac32(id)>.enc`
- 复用现有机制：oplog 的 `entity` 字段新增 `'category'` / `'tag'`；`If-Match` 条件写；冲突走 LWW
- **同名合并规则**（比 LWW 更重要）：
  ```
  拉取时若发现远端标签 name 与本地某标签相同但 id 不同
    → 保留 usage_count 大的一方 id
    → 把另一方的 entry_tag 关联全部改指到保留方
    → 写入一条 merge 记录到 oplog（可审计）
  ```
- 删除分类不删条目：只把 `entry_category` 关联清掉，条目变「未分类」

### 2.5 交互方式

| 操作 | 行为 |
|---|---|
| 给笔记选分类 | 编辑器顶部一个下拉，**单选**；输入即搜索；允许「＋ 新建"xxx"」 |
| 打标签 | 编辑器内输入 `#` 触发，或标题下方标签行点 `＋`；上限 8 个，超出提示 |
| AI 建议 | 新建笔记保存后，AI 在右侧面板给出 1 个分类建议 + 2~4 个标签，一键采纳（**不自动写入**） |
| 拖拽 | 管理页内可拖拽排序、拖到父分类下变成二级 |
| 筛选 | 列表左侧点分类/标签 → 多选（标签 AND，分类 OR） |
| 删除分类 | 二次确认，文案明确：「48 条笔记会移到未分类，不会被删除」 |

### 2.6 实现范围

| 一期 | 二期 |
|---|---|
| 两级分类树、标签 CRUD、编辑器内选择、列表筛选、管理页 | 智能标签（AI 自动聚类建议）、标签合并向导、分类模板 |

## 3. 归档网站页面

### 3.1 现状与缺口

现有只有「阅读器」（第 04 屏）。缺的是**总览**：用户看不到自己存了多少网站、哪些已经打不开、占了多少空间、该清哪些。

### 3.2 页面结构

│ 归档                   88 个 · 占用 1.2 GB      [＋ 归档网址] │

│  已失效    5  │  ─────────────────────────────────────────    │

│  仅元数据  3  │    blog.example.org · 08-12 · 已失效          │
│              │    [已回退快照] · 可试 Wayback                │
│ 站点          │  ─────────────────────────────────────────    │
│  example.com  │  ▣ …                                          │
│  github.com   │                                               │
│  …            │                                               │
├──────────────┴───────────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────┘

### 3.3 数据字段

`entry.meta`（kind=5）扩展：

```json
{
  "url": "https://example.com/post/123",
  "final_url": "https://example.com/post/123?utm=x",
  "site": "example.com",
  "title": "RFC 6578：WebDAV 的增量同步机制",
  "author": "…",
  "published_at": 1730000000000,
  "archive_status": "full",       // none|metadata|text|full|blocked|paywalled|dead
  "http_status": 200,
  "last_checked_at": 1731052800000,
  "recheck_policy": "monthly",    // weekly|monthly|never
  "snapshot_bytes": 412000,
  "reading_time_min": 8,
  "excerpt": "sync-collection 报告允许客户端…",
  "changed": false,               // 内容是否变更过（simhash 比对）
  "wayback_url": null             // 死链时回退地址
}
```

新增检查历史表（本地，不同步）：

```sql
CREATE TABLE link_check (
  entry_id    TEXT NOT NULL,
  checked_at  INTEGER NOT NULL,
  http_status INTEGER,
  result      TEXT NOT NULL,   -- ok | dead | restricted | unreachable | changed
  final_url   TEXT,
  simhash     TEXT,            // 内容指纹，用于变更检测
  PRIMARY KEY (entry_id, checked_at)
);
```

### 3.4 交互方式

| 操作 | 行为 |
|---|---|
| 归档网址 | 顶部按钮 / 全局 `⌘⇧U` / 粘贴自动识别；3 秒内完成正文层，快照后台生成 |
| 点条目 | 进阅读器（04 屏） |
| 「重抓」 | 单条重抓，保留旧快照为历史版本 |
| 死链处理 | 标记 `dead` → 自动查 Wayback availability API → 有则显示「查看 2019 存档」 |
| 批量检查 | 按 `recheck_policy` 分批；前台补偿执行，不承诺后台 |
| 清理 | 按 LRU 把最老的 `full` 降级为 `text`（删快照，留正文），不删条目 |
| 配额守卫 | 云端用量 > 80% 时，新归档只存正文层并提示 |

### 3.5 实现范围

| 一期 | 二期 |
|---|---|
| 总览列表、状态筛选、站点聚合、重抓、死链标记、Wayback 回退、配额清理 | 站点级 RSS 订阅、整站归档、全文变更 diff 视图 |

## 4. 账号分类、自定义字段与备注

### 4.1 现状与缺口

现有账号只有固定 4 个字段（用户名/密码/TOTP/网址），且分类只是一个筛选标签。真实场景里账号需要：任意自定义字段（PIN、安全提问、恢复码、服务器地址）、自由备注、以及真正的分类归属。

### 4.2 页面结构

**A. 账号列表（升级第 10 屏）** —— 左栏分类改为「分类树 + 智能分组」：

│     开发     9   │
│  ▸ 个人      15  │
│  ▸ 金融       9  │

└──────────────────────────────────────────────────────────────┘

### 4.3 数据字段

`credential` 独立表（`kind=6` 的 entry 一对一）：

```sql
CREATE TABLE credential (
  entry_id            TEXT PRIMARY KEY,
  category_id         TEXT,              -- 关联 category(kind=6)
  username            TEXT,              -- 加密
  password            TEXT,              -- 加密
  totp_secret         TEXT,              -- 加密
  url                 TEXT,
  notes               TEXT,              -- 加密，自由备注
  custom_fields       TEXT,              -- 加密 JSON，见下
  password_updated_at INTEGER,
  strength            INTEGER,           -- 0~4，本地估算
  reused              INTEGER DEFAULT 0,
  leaked              INTEGER DEFAULT 0,
  favorite            INTEGER DEFAULT 0,
  icon_blob           TEXT               -- favicon 的 blob hash
);
```

`custom_fields` 结构（加密后整体存储）：

```json
[
  { "id": "f1", "label": "恢复码", "value": "xxxx-xxxx-xxxx",
    "type": "text", "secret": true,  "sort": 0 },
  { "id": "f2", "label": "PIN",    "value": "8842",
    "type": "text", "secret": true,  "sort": 1 },
  { "id": "f3", "label": "服务器", "value": "sftp.example.com",
    "type": "url",  "secret": false, "sort": 2 }
]
```

`type` 枚举：`text` / `url` / `email` / `phone` / `date` / `multiline`。

### 4.4 三条硬约束

**1. `secret: true` 的字段与密码同级对待**

- 编辑态默认掩码
- 复制后 30 秒清剪贴板
- **绝不进入任何 prompt 上下文**
- `get_credential` 工具返回时整体脱敏（只返回字段名，不返回值）

**2. AI 永远读不到明文**

`credential_health` 只返回统计；任何工具都不返回 `password` / `totp_secret` / `secret:true` 字段的 `value`。
这条在 `CredentialGuard` 里做代码级拦截，不靠 prompt 约束。

**3. 备注字段允许 AI 读，但要显式授权**

备注里可能有敏感信息（如「旧账号还能登录」）。默认 **L0 端侧**，云端模型需要逐次授权。

### 4.5 交互方式

| 操作 | 行为 |
|---|---|
| 新增/编辑 | 右侧抽屉打开，不是新页面（保持上下文） |
| 自定义字段 | 拖拽 `≡` 排序；`secret` 开关实时切换掩码；最多 20 个字段 |
| 备注 | 纯文本，支持 `⌘B` 加粗、列表；不做富文本 |
| 分类 | 单选下拉，输入即搜，可「＋ 新建」 |
| 收藏 | 星标，进「收藏」分组，可选置顶到列表顶部 |
| 密码生成 | 弹出生成器（长度/字符集/排除易混字符），生成后直接填入并标记 `password_updated_at` |
| 附件 | 一期只支持图片（恢复码截图、二维码），≤ 5 MB，加密后进 `blobs/` |

### 4.6 账号分组（分组体系）

账号的「分组」不是筛选标签，而是一套**独立于笔记分类**的归属体系（`category.kind = 6`）。

| | 分组 Group | 智能分组 Smart Group |
|---|---|---|
| 来源 | 用户手动建，两级树 | 系统按规则生成，**只读** |
| 数量 | 一条账号最多 1 个 | 一条账号可同时属于多个 |
| 举例 | 工作 › 开发、个人、金融 | 收藏 / 未分组 / 已泄露 / 重复 / 超期 / 无 TOTP |
| 用途 | 归属与字段模板 | 待办入口 |
| 删除 | 组内账号移到「未分组」，不删账号 | 不可删 |

**组内字段模板**（这是分组真正的价值）：同一分组可以预设自定义字段结构。
在「工作 › 开发」下新建账号，自动带上 `恢复码（私密）`、`团队名`、`部署环境` 三个字段。
这样用户不用每次手动加一遍。

**列表行为**：
- 左栏点分组 → 右侧只显示该组账号，且**该组的字段模板字段作为列显示**
- 点智能分组 → 按规则过滤（已泄露 → `credential.leaked = 1`）
- 账号可拖拽换组；拖到父分组则清空子分组

**数据字段**：复用 §2.3 的 `category` 表（`kind=6`），新增一张模板表：

```sql
CREATE TABLE category_field_template (
  category_id TEXT NOT NULL,
  label       TEXT NOT NULL,
  type        TEXT NOT NULL DEFAULT 'text',
  secret      INTEGER NOT NULL DEFAULT 0,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (category_id, label)
);
```

**同步**：模板随 `category` 一起走 `taxonomy/` 通道，加密后存储。

### 4.7 实现范围

| 一期 | 二期 |
|---|---|
| 分类树、自定义字段（含 secret）、备注、收藏、密码生成器、图片附件 | 字段模板（同一分类复用字段结构）、TOTP 扫码录入、Passkey 存储 |

## 5. 与现有系统的兼容性检查

| 面 | 影响 | 处理 |
|---|---|---|
| **数据模型** | `entry` 表结构**不变** | 分类/标签走关联表；日记/归档扩展全在 `meta` JSON；账号走独立表 |
| **同步** | 新增 `entity='category'/'tag'` | 复用 oplog + If-Match；新增 `/vault/taxonomy/` 目录；同名合并规则见 2.4 |
| **加密** | 账号新字段全部加密 | `custom_fields` 整体加密；`secret` 字段进 `CredentialGuard` 白名单 |
| **检索** | 分类/标签需要可搜 | `entry_fts.tags` 列写入标签名（逗号拼接）；分类不进 FTS，走结构化过滤 |
| **AI** | 工具集新增 | `list_categories` / `set_category`（confirm）/ `add_tags`（confirm）/ `credential_health`（扩展统计） |
| **视觉** | 全部新页面沿用 | 不规则圆角 `.wob-a~d`、虚线描边、硬阴影、红/蓝分工 |
| **性能** | `entry_count` / `usage_count` 冗余 | 异步更新（写队列），不阻塞主流程；每日校准一次 |

## 6. 验收标准

| # | 标准 |
|---|---|
| D1 | 日记可在月历上补写任意历史日期，`meta.date` 与 `created_at` 分离且同步后正确 |
| D2 | 两台设备同时给同一笔记设不同分类 → 合并后保留 HLC 较大者，不产生两条分类 |

| D7 | 自定义字段增删改排序后，跨设备同步结果一致 |
| D8 | 所有新页面在亮/暗两套主题下对比度 ≥ 4.5:1 |

## 7. 工作量估算

| 模块 | 人日 | 说明 |
|---|---|---|
| 日记总览页 + 补写 | 6 | 月历组件 + `diary_index` + 详情升级 |
| 分类与标签（含管理页） | 12 | **含同步引擎新增实体（3 天）** |
| 归档总览页 | 8 | 列表 + 状态筛选 + 重抓 + 死链 + 配额 |
| 账号分类/自定义字段/备注 | 10 | 编辑抽屉 + 加密字段 + Guard 扩展 |
| 回归测试 | 4 | 同步用例扩展到 26 条 |
| **合计** | **40 人日** | 约 2 个月（单人） |

**优先级建议**：先做「账号自定义字段」（用户呼声最高、独立性强、不碰同步引擎），再做「归档总览」，最后做「分类与标签」——因为它要动同步引擎，风险最高，值得放在同步回归测试成熟之后。
